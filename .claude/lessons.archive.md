## [gotcha] 2026-10-25 | a conventional commit scope cannot hold a comma, and the commit-msg hook refuses it only after the pre-commit gates pass

The phase 7 design gave commit 8 the subject `docs(write,auth): …`. The pre-commit gates ran and passed, and then the commit-msg hook refused the subject, because a scope is one word with no comma. ## [decision] 2026-10-25 | the 2.8.0 docs keep their v2.8.0 bytes under a banner, and the gate hashes bytes, not text

## [decision] 2026-10-18 | The root signs only through the tier variables and auth's token helper, so a dev checkout must run the auth bin once

## [gotcha] 2026-10-16 | `bun pm pack` changes `workspace:*` to the version number, also in devDependencies

The plan keeps `@ask-marcel/office-core` out of `dependencies`, because core is never published and an install would get a 404. Core stays only in `devDependencies` as `workspace:*`. `bun pm pack` changes that `workspace:*` to the version of core in the packed `package.json`, also in `devDependencies`. An install does not get devDependencies, so the packed package still installs. But a check that searches the packed manifest for `workspace:` finds nothing. `scripts/check-packed-package.ts` checks that core is in no field except `devDependencies`.
Rule for next time: check the packed `package.json` in the tarball, not the source manifest. Do not expect `workspace:*` in a packed file.

## [gotcha] 2026-10-16 | A spawned token helper gets the HOME and the ASKMARCEL_* variables of its caller, so a round-trip test must remove both

The token helper round trip spawns `dist/token.js` the way read spawns it. The child gets the environment of the parent. If the person who runs the test has `ASKMARCEL_TOKEN_BASIC` or `ASKMARCEL_TOKEN_COMMAND` set, or a real `~/.ask-marcel/` cache, the test uses those values and not the fixture. The test then passes or fails for the wrong reason, and it can write the real locator file. The round trip now gives the helper and the caller a temporary HOME and an environment with no `ASKMARCEL_*` variable.
Rule for next time: a test that spawns the CLI or the helper sets HOME (and USERPROFILE) to a temporary folder and removes every `ASKMARCEL_*` variable. Do a test of it with such a variable set to a bad value.

## [gotcha] 2026-10-10 | The read-bundle check must match plain "PUT", "PATCH" and "DELETE" strings, not `method: 'PUT'`

`scripts/check-read-bundle.ts` searches the built read bundle for the markers of write code. A pattern such as `method: 'PUT'` depends on the quotes and the layout that the bundler writes. It also misses a method name that the code gives as a plain argument, for example the network-error label in `wrapNetworkError(e, 'PUT', path, 'binary')`. Thus the check matches the quoted string alone (`"PUT"`, `"PATCH"`, `"DELETE"`, in any quote) and `createUploadSession`. The control bundle with `createWriteGraph` must show all four markers, or the check fails. A check that sees nothing must not pass.
Rule for next time: write a bundle marker against the built output, not against the source text. Always keep a control that must show the marker, so a marker that can no longer match turns the gate red.
Archived 2026-11-15: graduate, `scripts/check-read-bundle.ts:11-12, 27-28, 49-51` (quoted-string markers and a control that must show each marker).

## [gotcha] 2026-10-01 | `bun run <file>` puts a bun-backed `node` on PATH when no real node is installed, so "under node" probes silently run on bun

The bundle smokes spawn `node` and `bun` to test both runtimes the package promises. Started as `bun run scripts/x.ts`, bun injects its own `node` shim into PATH on a machine with no node, and every node probe then runs on bun while the log still says node. CI's ubuntu image ships a real node and the smoke job pins Node 20 with setup-node, so no run was affected, but the gate would fail open on a bun-only machine. The smokes now run as `bun scripts/x.ts` and print the node and bun versions they found.
Rule for next time: start a script that must exercise node as `bun <file>`, never `bun run <file>`, and have it log `node --version`.

## [gotcha] 2026-09-04 | Improving a below-90 file can BREAK the mutation gate, because `mutate:changed` aggregates only the diff and a small commit makes one weak file the whole score

`read-mail-attachment.ts` sat at 66.05 for months without ever failing CI: it rode inside larger changed sets, and the b23b11b run scored 10 files at an aggregate 91.02. Raising it to 75.93 and committing that improvement ALONE turned main red at 86.91, because the diff then held two files and the weak one dominated. The next commit was worse: base f623ccc gave a ONE-file diff, so the aggregate was literally that file's 88.06. A change that strictly improved the codebase failed the gate that the unimproved code had passed, purely because of how the commit was split.
Two corollaries. Commit granularity is a gate input, not just a review preference: a test-only commit that touches one sub-90 file is the worst possible shape, and pairing the fix with other work is legitimate rather than a dodge. And measuring locally proves nothing unless the file set matches the one CI will build. A local run on `read-mail-attachment.ts` + `docs.ts` reported 94.07 while CI, basing on the previous commit, mutated the single file and reported 88.06. That is the 2026-08-30 base-selection entry biting a second time in a new shape.
Rule for next time: before committing work that touches a file known to be under 90, compute the exact set CI will mutate (`git diff --name-only <the base CI will use>...HEAD`, which for a push is `github.event.before`) and run Stryker on precisely that list. If the file is alone in it, either bring the file over 90 in the same commit or land it together with the work that motivated it.
Archived 2026-11-15: archive, subject gone: the aggregate score of the diff no longer decides. `scripts/check-mutation-score.ts:6-9` holds each file to `break` (per-file gate, `4dd2639`, 2026-10-25).

## [gotcha] 2026-09-03 | Stryker's command runner keeps every killed mutant's whole test output, so a verbose CI listing times a thousand mutants blows `JSON.stringify` after the score has passed

Two pushes turned main red in the `mutate:changed` step with `RangeError: Invalid string length` thrown from `JSON.stringify` in `MutationTestReportHelper.reportAll`, both times AFTER the clear-text table had printed a passing score (97.00 on the group-post push, every file above 90). The command test runner stores a killed mutant's entire process output as its `statusReason`, and the report serialises all of them. On GitHub Actions `bun test` lists every test (5729 `(pass)` lines, 1.2 MB a run), so 1002 killed mutants meant roughly 1.2 GB of status reasons, past V8's string limit on the runner's Node 22. Locally the same suite prints 31 KB a run, which is why the 9-file run finished cleanly here at 96.42 and the crash never reproduced. Fixed in `ed112aa`: the command is `bash -o pipefail -c 'bun test 2>&1 | tail -n 20'`, so a status reason is the summary only and bun's exit code, the thing that decides killed versus survived, is preserved; proved red-path (a failing test exits 1 through the wrapper) and end to end (27 mutants, score 100, largest status reason 1551 characters under `GITHUB_ACTIONS=true`). Two traps around it: the sandbox excludes `scripts/` and `*.toml`, so the wrapper has to be inline in `stryker.conf.json`, not a script; and a push whose diff has no mutation-scope file skips the step, so a config-only fix is only exercised in CI by the next `src/` push.
Rule for next time: when a mutation run dies after printing its score, read the stack for the reporter before doubting the score, and size the per-mutant output the runner stores; anything the test runner prints per test is multiplied by the mutant count. Keep the command runner's output to a summary from day one.
Archived 2026-11-15: graduate, `read/stryker.conf.json:7-10` (same lines in `auth/`, `core/`, `write/`): `bash -o pipefail -c 'bun test --randomize 2>&1 | tail -n 20'` with the reason in `_commandRunner_comment`.

## [decision] 2026-08-31 | Tests may not touch the network, enforced by a preload rather than by review

Five tests in `auth.test.ts` POSTed a bogus refresh token to the live AAD token endpoint, because `auth.ts` called the global `fetch` and `createAuthManagerFromApi` offered nothing to inject. They passed when AAD answered quickly and hit the 5s test limit when it did not, so the suite's failure count moved between 0, 3 and 5 across runs on one unchanged tree. Blast radius was MEASURED, not guessed: a preload counting every real `fetch` reported exactly 5, all to one host. `createAuthManagerFromApi` gained an optional trailing `fetchFn` (defaulting to the global, so all 107 call sites are untouched) and the five pass a fake refusing with `400 invalid_grant`, exactly what AAD returns for a dead token, which is the answer they had been relying on the network to provide.
Injection alone would have left the door open, so `scripts/no-network-preload.ts` now replaces `globalThis.fetch` for every `bun test` run with one that throws, naming the URL and the injection points that exist instead. It lives in `bunfig.toml` under `[test] preload`, unlike `scripts/coverage-preload.ts`, which is spawned separately because it drags in heavy SDKs; a CLI `--preload` ADDS to the bunfig list, so the guard is active during coverage runs too. No escape hatch: anything needing a live service belongs in `scripts/qa-*`, outside `bun test`.
Rule for next time: when a flaky test is traced to an unmocked boundary, fix the boundary AND close the door, or the next one arrives unnoticed. And verify a guard in both directions: a guard that never fires is indistinguishable from no guard, so make it fire once on purpose.
Archived 2026-11-15: graduate, `bunfig.toml:10-11`, `core/bunfig.toml:2-3`, `auth/bunfig.toml:2-3`, `read/bunfig.toml:2-3`, `write/bunfig.toml:2-3` preload `scripts/no-network-preload.ts`. The general half (prove a guard fires) goes to promote P5.

## [gotcha] 2026-07-17 | The size gate and the mutation gate pull in OPPOSITE directions — the escape is landing test-only commits FIRST against already-shipped code

Gate 1 caps a commit at 300 lines (insertions + deletions); gate 8 requires >=90% mutation on the staged use-case files. A feature whose tests are what earn the score cannot satisfy both: `get-mail-signature`'s logo embedding was 332 lines because every test was load-bearing (measured — deferring ANY of them dropped the aggregate below the 141 kills it needed, so there was nothing to trim). Splitting code from tests fails the mutation gate instead; the tests cover code the SAME commit stages, and staging a file drags its WHOLE mutant surface in, not just the diff. The way out: land the tests as their own `test(...)` commit FIRST, written against the code as it is already shipped, then the feature commit is small enough. That is why C9 became four commits (convert's debt -> scan/envelope tests -> embedding -> a meta fix) instead of one, and every one passed both gates. The enabling trick is a path BUILDER in the test (`const bodyOf = (id) => ...`): the pre-commit tests pin today's URL, and the feature commit changes that URL in ONE line instead of thirty.
Corollary learned the hard way: DON'T reformat to hit the size gate. Prettier-collapsing fixtures moved 337 -> 332 because the gate counts deletions too, so rewriting lines that already exist in HEAD costs DOUBLE. Densifying a file that partly exists is self-defeating; split the commit instead.
Also: `check-commit-size.sh` counts insertions + deletions. Reading only the insertion count is how C4 shipped at 304 (the hook is inert in this clone — `core.hooksPath` unset — so nothing catches it but you).
Archived 2026-11-15: archive, subject gone: the pre-commit hook runs no mutation (`.githooks/pre-commit:8-11`), and CI mutates the whole pushed range (`.github/workflows/ci.yml:15-20`). The "deletions count too" fact is in `scripts/check-commit-size.sh:3`.

## [gotcha] 2026-07-17 | Stryker's incremental cache reports STALE survivors when only the TEST file changed — and the aggregate gate makes a low-scoring file un-touchable

`stryker.conf.json` sets `incremental: true` + `incrementalFile: reports/stryker-incremental.json`. The cache keys on the SOURCE file: add tests for existing code, re-run `mutate:changed`/`mutate:staged`/`--mutate <path>`, and Stryker replays the cached verdicts and prints a score that has never seen the new tests. `get-mail-signature.ts` read 86.67% twice in a row across two rounds of new tests (identical to the digit — the tell), then 91.33% the instant `rm -f reports/stryker-incremental.json` preceded the run. Nearly concluded the tests were worthless and went hunting for a design fix to a measurement bug. ALWAYS `rm -f reports/stryker-incremental.json` before a run whose point is to measure NEW TESTS against UNCHANGED source; an identical score across a round of test-writing is the signature, not a coincidence.
Second half, same session: the break threshold is evaluated on the AGGREGATE over the staged set, so a file's own debt becomes everyone's. `convert-mail-to-markdown.ts` sits at 88.24% ALONE (34 survivors / 289 mutants, mostly inert meta-block prose) and had never been imported by another command, so it had only ever been staged next to higher-scoring siblings — invisible debt. ## [gotcha] 2026-07-17 | An MCP stdio server's stdout purity is invisible to BOTH the unit tests AND a Client-based handshake — only a raw-stdout assertion catches a stray write

(2) Less obviously, a real stdio handshake through the SDK's own `Client` ALSO passes: injecting `process.stdout.write('STRAY BANNER\n')` into the `mcp` path produced a bundle whose raw stdout was literally `STRAY BANNER\n{"result":...}`, and a `StdioClientTransport` + `Client` probe still reported a clean 5-tool handshake — the SDK's `ReadBuffer` silently SKIPS lines it cannot parse, so a tolerant client hides the exact bug the gate exists to find. ## [gotcha] 2026-06-02 | Stryker counts `Timeout` mutants as KILLED — manual `mutation.json` parsing must too

A mutant that makes a loop run forever (e.g. `start < n` → `start >= n`, or `start += chunk` → `start -= chunk`) is reported with `status: "Timeout"`, and Stryker's break-threshold math counts Timeout as detected/**killed**. A hand-rolled `mutation.json` parser that only counts `status === "Killed"` (treating Timeout as a survivor) under-reports the score and disagrees with Stryker's own pass/fail — e.g. a real 90.91% read as 89.3%. Trust the `Final mutation score of N` line in Stryker's log; if parsing the JSON, count `Killed` + `Timeout` (and exclude `CompileError`/`NoCoverage` per your gate's intent).
Applies to: any script that parses `reports/mutation/mutation.json` to gate or report mutation score.
