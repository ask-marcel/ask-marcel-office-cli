## [gotcha] 2026-10-25 | a conventional commit scope cannot hold a comma, and the commit-msg hook refuses it only after the pre-commit gates pass

The phase 7 design gave commit 8 the subject `docs(write,auth): …`. The pre-commit gates ran and passed, and then the commit-msg hook refused the subject, because a scope is one word with no comma. No commit was made, and the gates had to run again with `docs: …`. `--no-verify` also skips the commit-msg hook, so commit 27 ran `scripts/check-commit-messages.sh` by hand.
Rule for next time: a subject that names two packages has no scope. Run `bash scripts/check-commit-messages.sh` on each planned subject before the series starts, and after each commit made with `--no-verify`.

## [decision] 2026-10-25 | the 2.8.0 docs keep their v2.8.0 bytes under a banner, and the gate hashes bytes, not text

## [decision] 2026-10-18 | The root signs only through the tier variables and auth's token helper, so a dev checkout must run the auth bin once

Package-split phase 4 (D1) took `login`, `logout`, `status` and `token` out of the root. The MCP `login` and `status` tools, `dist/token.js` and the record of the locator went too. `buildDeps` now always uses the env-then-helper token source. It takes an `ASKMARCEL_TOKEN_<TIER>` variable first. Else it runs the token helper: `ASKMARCEL_TOKEN_COMMAND`, else the entry that `~/.ask-marcel/token-helper.json` names, else `ask-marcel-office-auth token` on PATH. Only the auth bin writes the token cache and the locator. Thus `bun run start <command>` in a new checkout fails with `token_helper_unavailable` until an auth run records the helper. Rejected: a root fallback to the in-process ladder (two writers of the token cache again, which the split removes).
Rule for next time: in a dev checkout, run the auth bin once before a root command. Run it again when you change between the source and `dist/`, because the locator names the last one that ran. In an older entry, `ask-marcel-office login`, `status` and `token` mean `ask-marcel-office-auth login`, `status` and `token`.

## [gotcha] 2026-10-18 | As `nobody`, bun cannot read the CA bundle under /root, and a check that reads stdout and stderr together then fails on the warning

The 2026-10-10 entry runs the gates as `nobody` on a copy. The proxy CA bundle of a cloud session is in `/root/.ccr/`, which `nobody` cannot read. Thus bun prints a warning on stderr for each run that uses the network. `scripts/check-packed-package.ts` joins the stdout and the stderr of `bun pm pack`, and it takes the last line as the tarball path. So it took the warning as the path and failed. The tarball was correct. A copy of the bundle at `/opt/nbbun/ca-bundle.crt`, given in `NODE_EXTRA_CA_CERTS`, `SSL_CERT_FILE` and `CURL_CA_BUNDLE`, made the run clean.
Rule for next time: before a run as `nobody` that installs or packs, copy the CA bundle to a folder that `nobody` can read. Point the three variables at the copy. A script that reads a result from a child must read stdout only, and give stderr to the person.

## [gotcha] 2026-10-16 | `bun pm pack` changes `workspace:*` to the version number, also in devDependencies

The plan keeps `@ask-marcel/office-core` out of `dependencies`, because core is never published and an install would get a 404. Core stays only in `devDependencies` as `workspace:*`. `bun pm pack` changes that `workspace:*` to the version of core in the packed `package.json`, also in `devDependencies`. ## [gotcha] 2026-10-16 | A spawned token helper gets the HOME and the ASKMARCEL_* variables of its caller, so a round-trip test must remove both

The token helper round trip spawns `dist/token.js` the way read spawns it. The child gets the environment of the parent. If the person who runs the test has `ASKMARCEL_TOKEN_BASIC` or `ASKMARCEL_TOKEN_COMMAND` set, or a real `~/.ask-marcel/` cache, the test uses those values and not the fixture. The test then passes or fails for the wrong reason, and it can write the real locator file. The round trip now gives the helper and the caller a temporary HOME and an environment with no `ASKMARCEL_*` variable.
Rule for next time: a test that spawns the CLI or the helper sets HOME (and USERPROFILE) to a temporary folder and removes every `ASKMARCEL_*` variable. Do a test of it with such a variable set to a bad value.

## [gotcha] 2026-10-10 | The read-bundle check must match plain "PUT", "PATCH" and "DELETE" strings, not `method: 'PUT'`

`scripts/check-read-bundle.ts` searches the built read bundle for the markers of write code. A pattern such as `method: 'PUT'` depends on the quotes and the layout that the bundler writes. It also misses a method name that the code gives as a plain argument, for example the network-error label in `wrapNetworkError(e, 'PUT', path, 'binary')`. Thus the check matches the quoted string alone (`"PUT"`, `"PATCH"`, `"DELETE"`, in any quote) and `createUploadSession`. The control bundle with `createWriteGraph` must show all four markers, or the check fails. A check that sees nothing must not pass.
Rule for next time: write a bundle marker against the built output, not against the source text. Always keep a control that must show the marker, so a marker that can no longer match turns the gate red.
Archived 2026-11-15: graduate, `scripts/check-read-bundle.ts:11-12, 27-28, 49-51` (quoted-string markers and a control that must show each marker).

## [gotcha] 2026-10-04 | `bun run mutate:changed` does not start when the tests run as root

Seven tests in the Node and Bun filesystem adapter suites make a file or a directory unreadable or read-only, and then expect `io_failed`. Root ignores these permissions, so the seven tests fail in a container that runs as root, for example a cloud session. Stryker first runs the full suite with no mutants, and it stops when a test fails. Thus `mutate:changed` and `mutate:staged` do not start. The step 9 run used a Stryker config in the session scratchpad: the same file scope, with the two filesystem adapter test files excluded. CI does not run as root and is not affected.
Rule for next time: as root, count the failures before you trust a gate. If only the seven filesystem `io_failed` tests fail, run Stryker with a scoped config that excludes the two filesystem adapter test files. Do not change the tests or the shared Stryker config for this.

## [gotcha] 2026-10-04 | as root, seven chmod-based tests fail and stryker cannot start

A cloud session runs `bun test` as uid 0, and root ignores the `chmod` modes that seven tests in `src/infra/filesystem-bun.test.ts` and `filesystem-node.test.ts` use to make a file unreadable or a directory read-only, so they fail on an untouched tree while CI, which runs as an ordinary user, stays green. The cost lands on mutation testing: Stryker's dry run needs a fully green suite, so a local `mutate:changed` cannot start at all. On 2026-10-04 a scratchpad copy of `stryker.conf.json` whose command ran every test file except those two measured `docs.ts` at 126 of 126 killed, and CI's mutation step passed on the same commit. Leaving tests out can only let a mutant survive, never kill one, so a score measured this way is a lower bound on CI's and a pass is a safe pass.
Rule for next time: when `id -u` prints 0, read those seven failures as the environment rather than a regression, and measure mutation through a scratchpad config that runs `bun test $(find ./src -name "*.test.ts" ! -name filesystem-bun.test.ts ! -name filesystem-node.test.ts)`, never by editing the repo's `stryker.conf.json`.

## [mistake] 2026-10-04 | a stale `origin/<branch>` ref turned a "fast-forward" push into a new remote branch

The session branch had a remote-tracking ref at the starting commit, so the push was offered to the user as a fast-forward that published nothing new, and `git merge-base --is-ancestor origin/<branch> HEAD` agreed. The `git fetch origin <branch>` run just before it had failed with "couldn't find remote ref": the branch did not exist on GitHub, and the ref was a leftover in the clone. The fetch was not chained to the push with `&&`, so its failure stopped nothing, and the push printed `* [new branch]`. No content leaked, since the commit was already on main, but a trunk-only repo gained a branch on the strength of a claim checked only against a local ref (the 2026-08-27 stale `origin/main` entry, in a new shape).
Rule for next time: before calling a push a fast-forward, ask the remote, where `git ls-remote --heads origin <branch>` printing nothing means the push creates the branch; chain the fetch and the push with `&&`, and report a `[new branch]` line as the fact it is.
Archived 2026-11-15: merge (M8, survivor M8), merged into "a stale `origin/*` ref is no statement about the remote: ask the remote before you call a push scope".

## [gotcha] 2026-10-03 | Bare `prettier --write` ignores this repo's style: the options live in eslint.config.js

There is no `.prettierrc`. The formatting options (single quotes, 180 columns, lf, es5 trailing commas) are arguments of the `prettier/prettier` rule in `eslint.config.js`, which is why `bun run lint` reports formatting and fails on any warning. A bare `bunx prettier --write` finds no config, falls back to prettier's defaults (double quotes, 80 columns) and rewrites every line of the file. It happened on 2026-10-02 during phase 1 step 6, to `src/infra/auth.ts` and `src/infra/auth-browser.ts`; both came back from copies taken just before the run, so nothing was lost, but a run without those copies would have buried the change in a whole-file reformat.
Rule for next time: format with `bunx eslint --fix <files>` and check with `bun run lint`; never call prettier directly. Copy a file aside before any bulk rewrite.
Archived 2026-11-15: merge (M10, survivor M10), merged into "the lint options live in eslint.base.js: format with `bunx eslint --fix`, and change rule severity there, never inline".

## [gotcha] 2026-10-01 | `bun run <file>` puts a bun-backed `node` on PATH when no real node is installed, so "under node" probes silently run on bun

The bundle smokes spawn `node` and `bun` to test both runtimes the package promises. The chat commits of 2026-09-19 took the signed-in user's object id straight from a live substrate probe and used it as the `OID` fixture of three chat tests, where it stood for "the signed-in user" in the mentions and `--mentions-me` scenarios. ## [gotcha] 2026-09-04 | Improving a below-90 file can BREAK the mutation gate, because `mutate:changed` aggregates only the diff and a small commit makes one weak file the whole score

`read-mail-attachment.ts` sat at 66.05 for months without ever failing CI: it rode inside larger changed sets, and the b23b11b run scored 10 files at an aggregate 91.02. ## [gotcha] 2026-06-02 | Stryker counts `Timeout` mutants as KILLED — manual `mutation.json` parsing must too

A mutant that makes a loop run forever (e.g. `start < n` → `start >= n`, or `start += chunk` → `start -= chunk`) is reported with `status: "Timeout"`, and Stryker's break-threshold math counts Timeout as detected/**killed**. A hand-rolled `mutation.json` parser that only counts `status === "Killed"` (treating Timeout as a survivor) under-reports the score and disagrees with Stryker's own pass/fail — e.g. a real 90.91% read as 89.3%. Trust the `Final mutation score of N` line in Stryker's log; if parsing the JSON, count `Killed` + `Timeout` (and exclude `CompileError`/`NoCoverage` per your gate's intent).
Applies to: any script that parses `reports/mutation/mutation.json` to gate or report mutation score.
Archived 2026-11-15: graduate, `scripts/check-mutation-score.ts:50-54`: `DETECTED = ['Killed', 'Timeout']`. It is the one script that parses `mutation.json`.
