## [gotcha] 2026-09-04 | Improving a below-90 file can BREAK the mutation gate, because `mutate:changed` aggregates only the diff and a small commit makes one weak file the whole score

`read-mail-attachment.ts` sat at 66.05 for months without ever failing CI: it rode inside larger changed sets, and the b23b11b run scored 10 files at an aggregate 91.02. Raising it to 75.93 and committing that improvement ALONE turned main red at 86.91, because the diff then held two files and the weak one dominated. The next commit was worse: base f623ccc gave a ONE-file diff, so the aggregate was literally that file's 88.06. A change that strictly improved the codebase failed the gate that the unimproved code had passed, purely because of how the commit was split.
Two corollaries. Commit granularity is a gate input, not just a review preference: a test-only commit that touches one sub-90 file is the worst possible shape, and pairing the fix with other work is legitimate rather than a dodge. And measuring locally proves nothing unless the file set matches the one CI will build. A local run on `read-mail-attachment.ts` + `docs.ts` reported 94.07 while CI, basing on the previous commit, mutated the single file and reported 88.06. That is the 2026-08-30 base-selection entry biting a second time in a new shape.
Rule for next time: before committing work that touches a file known to be under 90, compute the exact set CI will mutate (`git diff --name-only <the base CI will use>...HEAD`, which for a push is `github.event.before`) and run Stryker on precisely that list. If the file is alone in it, either bring the file over 90 in the same commit or land it together with the work that motivated it.
Archived 2026-11-15: archive, subject gone: the aggregate score of the diff no longer decides. `scripts/check-mutation-score.ts:6-9` holds each file to `break` (per-file gate, `4dd2639`, 2026-10-25).

## [gotcha] 2026-07-17 | The size gate and the mutation gate pull in OPPOSITE directions — the escape is landing test-only commits FIRST against already-shipped code

Gate 1 caps a commit at 300 lines (insertions + deletions); gate 8 requires >=90% mutation on the staged use-case files. A feature whose tests are what earn the score cannot satisfy both: `get-mail-signature`'s logo embedding was 332 lines because every test was load-bearing (measured — deferring ANY of them dropped the aggregate below the 141 kills it needed, so there was nothing to trim). Splitting code from tests fails the mutation gate instead; the tests cover code the SAME commit stages, and staging a file drags its WHOLE mutant surface in, not just the diff. The way out: land the tests as their own `test(...)` commit FIRST, written against the code as it is already shipped, then the feature commit is small enough. That is why C9 became four commits (convert's debt -> scan/envelope tests -> embedding -> a meta fix) instead of one, and every one passed both gates. The enabling trick is a path BUILDER in the test (`const bodyOf = (id) => ...`): the pre-commit tests pin today's URL, and the feature commit changes that URL in ONE line instead of thirty.
Corollary learned the hard way: DON'T reformat to hit the size gate. Prettier-collapsing fixtures moved 337 -> 332 because the gate counts deletions too, so rewriting lines that already exist in HEAD costs DOUBLE. Densifying a file that partly exists is self-defeating; split the commit instead.
Also: `check-commit-size.sh` counts insertions + deletions. Reading only the insertion count is how C4 shipped at 304 (the hook is inert in this clone — `core.hooksPath` unset — so nothing catches it but you).
Archived 2026-11-15: archive, subject gone: the pre-commit hook runs no mutation (`.githooks/pre-commit:8-11`), and CI mutates the whole pushed range (`.github/workflows/ci.yml:15-20`). The "deletions count too" fact is in `scripts/check-commit-size.sh:3`.

## [gotcha] 2026-07-17 | Stryker's incremental cache reports STALE survivors when only the TEST file changed — and the aggregate gate makes a low-scoring file un-touchable

`stryker.conf.json` sets `incremental: true` + `incrementalFile: reports/stryker-incremental.json`. The cache keys on the SOURCE file: add tests for existing code, re-run `mutate:changed`/`mutate:staged`/`--mutate <path>`, and Stryker replays the cached verdicts and prints a score that has never seen the new tests. `get-mail-signature.ts` read 86.67% twice in a row across two rounds of new tests (identical to the digit — the tell), then 91.33% the instant `rm -f reports/stryker-incremental.json` preceded the run. Nearly concluded the tests were worthless and went hunting for a design fix to a measurement bug. ALWAYS `rm -f reports/stryker-incremental.json` before a run whose point is to measure NEW TESTS against UNCHANGED source; an identical score across a round of test-writing is the signature, not a coincidence.
Second half, same session: the break threshold is evaluated on the AGGREGATE over the staged set, so a file's own debt becomes everyone's. `convert-mail-to-markdown.ts` sits at 88.24% ALONE (34 survivors / 289 mutants, mostly inert meta-block prose) and had never been imported by another command, so it had only ever been staged next to higher-scoring siblings — invisible debt. Widening its export by THREE LINES for `get-mail-signature` dragged all 289 mutants into the gate and put the aggregate at 84.51%: the arithmetic then demanded 93.4% from the new file just to break even, and NO amount of testing the new code would have cleared it if the new file were small. It worked here only because get-mail-signature.ts is 150 mutants and went to 95.33%. A small file touching that one cannot pass at all.
Rule for next time: before touching a file you have not measured, run `bunx stryker run --mutate <that-file>` ALONE (cache cleared) and learn its solo score — if it is under 90, either raise it first in its own commit or expect to carry it. And when a gate fails, score YOUR file alone before redesigning: it separates your debt from the debt you inherited, which is a different conversation with a different fix.
Archived 2026-11-15: archive, superseded by entry 23 (2026-08-31, `mutate:changed` and `mutate:staged` use a throwaway `--incrementalFile`) and by the per-file gate (`scripts/check-mutation-score.ts:6-9`). Entry 49 (tightened) records its wrong "inert" claim.

## [decision] 2026-07-16 | `login` re-captures the elevated token itself when it is missing (supersedes the 2026-07-13 "login is a slim confirmation, --force is the mechanism" decision)

The 2026-07-13 entry was right about the mechanism and wrong about the signpost, and the gap was a loop with no exit: a command needing elevated said "run `ask-marcel-office login`"; `login` found a valid cached BASIC token, returned on the cache rung, printed `authenticated` — and never re-captured elevated, which carries no refresh token of its own; the command then failed identically. Forever. The user hit it live. `login.execute` now escalates to `getAccessToken({force:true})` when `getCachedElevatedInfo()` reports elevated unavailable — the SAME rung `--force` uses, deliberately: the browser adapter's `freshCachedToken` probe short-circuits the dance when a valid token is cached and only the forced path suppresses it, so a hand-rolled re-capture would silently no-op (exactly how `--force` itself shipped broken once). An already-forced login does not escalate again, so a tenant whose elevated capture keeps failing gets one browser per invocation, not two. Both halves verified live: elevated missing -> browser opens; elevated present -> no browser, instant. Note the remedy is NOT uniform across the three secondary tiers, though one shared message claimed it was: chatsvcagg/ic3 ride the shared RT and self-heal headlessly, so plain `login` is right for them and `--force` costs a browser they never needed.
Rule for next time: the false absolute ("the only way to refresh...") had propagated to FOUR places (the elevated fail-fast message, `scopes-check`'s hint, `scopes-check`'s summary, the README) and one change falsified all of them at once — when writing a remedy into a message, do not write "the only way" unless you have checked every tier it covers.

## [decision] 2026-07-13 | `login` reports all four cached tokens with time-left + refresh route; `login --force` forces a full browser re-capture

`login` (including a re-run while already signed in) now prints all four cached tokens — basic, elevated (M365ChatClient), and the two Teams-chat substrate tokens (chatsvcagg / ic3) — each as `{ available, expiresInSeconds?, refresh: 'automatic' | 'interactive', reason? }`, replacing the old bare `{ status: 'authenticated' }` and the undocumented `elevated: 'captured' | 'failed'` field. basic/chatsvcagg/ic3 are `refresh: 'automatic'` (they ride the shared refresh_token / substrate self-heal); elevated is `refresh: 'interactive'` because it carries no refresh_token of its own and is re-captured only during a browser login. A failed elevated capture this run surfaces its `reason` on the elevated token. `login --force` (new flag) skips the cache + refresh rungs in `getAccessToken({ force })` and goes straight to `acquireViaBrowserShared()`, re-capturing every token in one pass (the persistent browser profile is reused, so credentials are usually not re-entered).
Rule for next time: a cache-hit `login` does NOT renew the elevated token (no refresh_token) — direct users to `login --force`, the only way to refresh it while the basic token is still valid. The four fresh-token buffers all share `ELEVATED_BUFFER_SECONDS` (300s), so `available` agrees with what each token getter would decide.

## [decision] 2026-07-13 | Four-token status is computed once in graph.getCachedTokenInfo; scopes-check surfaces it additively, login shapes it via a pure helper

The token-status data (basic from the JWT, elevated/chatsvcagg/ic3 from the auth manager's decode-only `getCached*Info` getters) is assembled once in `graph.getCachedTokenInfo()` -> `TokenInfo`. `scopes-check` returns it directly, so it gained `chatsvcagg` / `ic3` ADDITIVELY (existing top-level `expiresInSeconds` + `elevated` unchanged — non-breaking for anything already parsing it). `login`'s envelope is shaped by the pure `buildLoginStatus` helper (`login-status.ts`, use-case tier, mutation-gated 100%) that maps the four tiers to the object-keyed `{ status, tokens, hint }` and attaches the fixed refresh markers + the `login --force` hint; `cli.ts` just reads `getCachedTokenInfo()` and calls it. The new substrate getters (`getCachedChatsvcaggInfo` / `getCachedIc3Info`) mirror `getCachedElevatedInfo` exactly — same 300s buffer, plain `{ available, expiresInSeconds }` not `Result` (a decode-only preflight, not an IO boundary).
Rule for next time: to add a token tier to the login / scopes-check status, add a `getCached<Tier>Info` to the AuthManager (optional, mirroring the elevated one), populate it in `getCachedTokenInfo` with the `{ available: false }` fallback, and it appears in scopes-check for free; login picks it up via `buildLoginStatus`.

## [decision] 2026-07-13 | scopes-check is the single detailed token-status view; login is a slim auth confirmation (2.2.0)

The four-token status dashboard added to `login` in 2.1.0 was reworked in 2.2.0: `login` slimmed to `{ status: 'authenticated', available: string[], hint }` (which tiers are available + a pointer to `scopes-check` and `login --force`), and the detailed per-token view moved to `scopes-check` — the natural home because it is the ONLY side-effect-free read (pure local decode, no Graph call, no browser) and already listed scopes. This keeps the safe pre-flight (agents check status without risking an auth side-effect) while removing the login/scopes-check overlap. `scopes-check` now reports, per tier, `{ available, expiresInSeconds?, scopes, refresh }` where `scopes` is that token's OWN grant decoded from its `scp` claim: the four tokens carry DISTINCT sets (basic ~31 Graph scopes, elevated ~20 different Graph scopes, chatsvcagg `user_impersonation`, ic3 `Teams.AccessAsUser.All`). Shape is ADDITIVE (flat top-level basic fields unchanged → non-breaking vs 2.0/2.1). The `refresh` marker is a fixed per-tier property assembled in `getCachedTokenInfo` (graph-client); scopes are decoded in the auth-layer `getCached*Info` (they hold the tokens) and flow through `CachedTierInfo`.
Rule for next time: keep `scopes-check` side-effect-free (it is the LLM safe pre-flight) and put token/scope DETAIL there; keep `login` an action that prints only a confirmation. The meta.test summary-flag validator extracts any `--flag` from a registry command's summary and requires it be a real option on THAT command, so do not write another command's flag (e.g. `login --force`) into a registry command's summary — reword (responseShape is exempt).

## [gotcha] 2026-06-16 | The token-refresh fallback opened the extension/Chrome capture per command — a popup storm in batch use

Command-path token re-auth (`getAccessToken` → `acquireViaBrowserShared` → `systemBrowserAuth`, `src/infra/auth.ts`) fell back to the system-browser + companion-extension capture (the user's default browser — Chrome, in an incognito-looking window with an `ask_marcel_port=` callback) whenever the silent `refresh_token` refresh failed. The CLI runs ONE process per command and the in-flight dedup (`recaptureElevatedShared`) is intra-process only, so a batch/agent run with a stale token opened one capture window PER command — a popup storm (the maintainer hit it live during a QA sweep, QA E-01). Fix is at the composition root: `build-deps.ts` builds the command-path AuthManager with `skipSystemBrowser: true` + `usePlaywrightFallback: true` (the same config the default `login` already uses), so re-auth opens a headed Edge sign-in (the Playwright path prefers the `msedge` channel and launches `headless:false`) that captures all four tokens in one window — one login ends the cascade. (Superseded in 2.0.0: the companion extension and the whole system-browser / localhost-callback capture path were removed — `login` is Playwright-only, and a lapsed chatsvcagg/ic3 substrate token now self-heals via a headless refresh of the shared Teams RT before any fail-fast.)
Rule for next time: the extension / Chrome-incognito capture is LOGIN-ONLY; command-path token acquisition must never launch it — cache → silent refresh → (only if that fails) a headed Edge login, never a per-command extension popup.

## [gotcha] 2026-06-01 | the machine-readable mutation report needs the `json` reporter added — `mutation.json` is otherwise stale

`stryker.conf.json` here emits `["clear-text", "progress", "html"]` — NO `json` reporter — so `reports/mutation/mutation.json` is NOT refreshed by a normal run; it retains whatever a prior run left behind, and parsing it (per the 2026-05-30 lesson) then reports STALE survivors as if current. To get an accurate machine-readable survivor set you must temporarily add `"json"` to `reporters` (alongside `"incremental": false`), run, parse `mutation.json` for `status === "Survived"`, then restore the config before committing. `reports/` is gitignored, so a stale `mutation.json` lingers silently with no hint it is out of date.
Affects: any scoped or full `bunx stryker run` where you parse `mutation.json` to close the 90% gate.
Archived 2026-11-15: archive, subject gone: each `stryker.conf.json` lists `"json"` in `reporters` (`read/stryker.conf.json`, line with `"reporters"`), and `scripts/check-mutation-score.ts` reads that report on each run.

## [gotcha] 2026-05-30 | Stryker `incremental` reports optimistically — `rm`-ing the file is not enough; set `incremental: false`

The 2026-05-29 note said `rm -f reports/stryker-incremental.json` fixes stale verdicts. It does not fully: with `testRunner: command` + `incremental: true`, a scoped `--mutate` run still over-credits kills (measured 85.4% where a truly-clean run was 84.0%) even after deleting the file. The CLI flags do not help — `--incremental false` is parsed as a config-file path ("Invalid config file 'false'") and `--no-incremental` is rejected as an unknown option. The only reliable accurate gate is editing `stryker.conf.json` to `"incremental": false` (optionally `"cleanTempDir": false` to keep the sandbox for inspection), running, then restoring. Restore both before committing — they are dev-speed defaults, not part of a feature change.
Affects: any scoped `bunx stryker run --mutate <file>` where you need a trustworthy pass/fail against the 90% break threshold.

## [gotcha] 2026-05-06 | elevated capture deadline must accommodate federated-IdP interactive auth

The first elevated-token capture in `src/infra/browser-auth.ts` capped the poll deadline at 60 s, assuming silent SSO would always succeed via persistent profile cookies. On third-party-IdP-fronted tenants the passive WS-Fed session expires every few hours, after which `m365.cloud.microsoft/*` redirects through `idp.<tenant>.com/.../sso/wsfed/passive` and stays there pending interactive sign-in. 60 s is not enough — bump the deadline to the full `pollDeadlineMs` (5 min default) so the user has time to finish the IdP sign-in inside the visible Edge popup.
Affects: `src/infra/browser-auth.ts` `acquireElevatedToken`; any tenant where the Microsoft-Graph IdP is federated to a third party with shorter session lifetimes than Microsoft's own SSO.
