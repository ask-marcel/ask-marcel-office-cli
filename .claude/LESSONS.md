## [gotcha] 2026-07-17 | Graph does NOT always emit `appendonsend` — `QUOTE_BOUNDARIES`' marker families are load-bearing, not redundancy. Live-proven: Exchange SafeHTML preserves `divRplyFwdMsg` across a PATCH

Live smoke of the mail-draft splice against a real mailbox: `POST /createReplyAll` returned a draft carrying `divRplyFwdMsg` and NO `appendonsend` at all. The design doc assumed `appendonsend` PRECEDES `divRplyFwdMsg` (the "type above this line" marker; C1's own fixture encodes that order) and described the three marker families in `mail-quote-stripper.ts` as "boundary redundancy" mitigating SafeHTML risk. They are not redundancy — they are the mechanism. An implementation keyed on `appendonsend` alone finds no boundary, and every `--comment` revise refuses with "no quoted reply history". Never collapse `QUOTE_BOUNDARIES` to one family, and never trust a marker's presence from one tenant's sample; `findQuoteBoundary` takes the EARLIEST of whatever is actually there, which is exactly why this passed.
The main external risk is now DISPROVEN, and it needed a real mailbox to do it: Exchange SafeHTML round-trips `divRplyFwdMsg` through `PATCH /me/messages/{id}` unharmed. Proof is the idempotency run, not the create: three PATCHes, comment counts 1/0/0 -> 0/1/0 -> 0/0/1 (each `--comment` REPLACES, never stacks), `divRplyFwdMsg` present after every one, body length stable at ~18.9K. `<head><style>`, the quoted From/Sent block, and raw `<b>`/`&amp;` all survived (not escaped). Forward path identical. Every offline gate had passed against fakes that model our ASSUMPTION of Graph — none of them could have caught a SafeHTML rewrite.
Supersedes one claim in the Stryker entry below: it says `convert-mail-to-markdown.ts`'s 34 survivors were "mostly inert meta-block prose". That was a guess and it was WRONG — 0 of 34 were in the meta block; all 34 were real code (the three ways `fetchInlineImageBytes` abandons one image, each conjunct of `isInlineImage`, the attachments-list failure note). 11 tests killed 8 of them and took the file 88.24 -> 91.00. Do not dismiss a survivor set as inert without reading it: the excuse that a file "can't" be improved was one grep away from being falsified.
Also live: `--reply-all false` -> 1 recipient vs 7 to + 2 cc by default; `--cc-recipients ""` -> cc 2 -> 0 with toRecipients untouched; `get-mail-signature` -> a real 2135-byte block. NOT exercised live: the logo embedding (`inlinedImages: 0` — that mailbox's signature carries no cid: image), so C9b's embed/oversize/note paths remain fake-only.

## [gotcha] 2026-07-17 | Stryker's incremental cache reports STALE survivors when only the TEST file changed — and the aggregate gate makes a low-scoring file un-touchable

`stryker.conf.json` sets `incremental: true` + `incrementalFile: reports/stryker-incremental.json`. The cache keys on the SOURCE file: add tests for existing code, re-run `mutate:changed`/`mutate:staged`/`--mutate <path>`, and Stryker replays the cached verdicts and prints a score that has never seen the new tests. `get-mail-signature.ts` read 86.67% twice in a row across two rounds of new tests (identical to the digit — the tell), then 91.33% the instant `rm -f reports/stryker-incremental.json` preceded the run. Nearly concluded the tests were worthless and went hunting for a design fix to a measurement bug. ALWAYS `rm -f reports/stryker-incremental.json` before a run whose point is to measure NEW TESTS against UNCHANGED source; an identical score across a round of test-writing is the signature, not a coincidence.
Second half, same session: the break threshold is evaluated on the AGGREGATE over the staged set, so a file's own debt becomes everyone's. `convert-mail-to-markdown.ts` sits at 88.24% ALONE (34 survivors / 289 mutants, mostly inert meta-block prose) and had never been imported by another command, so it had only ever been staged next to higher-scoring siblings — invisible debt. Widening its export by THREE LINES for `get-mail-signature` dragged all 289 mutants into the gate and put the aggregate at 84.51%: the arithmetic then demanded 93.4% from the new file just to break even, and NO amount of testing the new code would have cleared it if the new file were small. It worked here only because get-mail-signature.ts is 150 mutants and went to 95.33%. A small file touching that one cannot pass at all.
Rule for next time: before touching a file you have not measured, run `bunx stryker run --mutate <that-file>` ALONE (cache cleared) and learn its solo score — if it is under 90, either raise it first in its own commit or expect to carry it. And when a gate fails, score YOUR file alone before redesigning: it separates your debt from the debt you inherited, which is a different conversation with a different fix.

## [decision] 2026-07-16 | A file in a tenant you are a GUEST in is readable via a guest token redeemed from the shared refresh token against THAT tenant's authority

`401 invalidAudienceUri: Invalid audience Uri '00000003-0000-0ff1-ce00-000000000000'` (SharePoint Online's app id) on a partner tenant's sharing URL is the TENANT boundary, and nothing else. Live-probed, all four combinations: it is NOT scopes (basic and elevated carry identical `Files.ReadWrite.All` + `Sites.ReadWrite.All`), NOT the ODSP appid allow-list (elevated fails identically to basic — do not reach for `getBinaryElevated` here, the 2026-05-06 reflex is wrong for this error), and NOT a missing `Prefer: redeemSharingLink`. Home-tenant Graph simply cannot mint an SPO token for a foreign tenant. The fix: derive the tenant from the URL host (`contoso.sharepoint.com` -> strip `-my` -> `contoso.onmicrosoft.com` -> that tenant's PUBLIC OIDC discovery doc -> tid), then redeem the shared FOCI refresh_token against `login.microsoftonline.com/{tid}/oauth2/v2.0/token`. `Origin: https://teams.microsoft.com` is MANDATORY — the Teams client is an SPA registration and Entra rejects SPA RT redemption that is not cross-origin with `AADSTS9002327`, BEFORE evaluating the grant, so its absence reads as "the tenant refused you" and will send you down the wrong path (it made the first probe report "cross-tenant is impossible"). The guest token reads that tenant's WHOLE `/drives` surface (metadata 200, `/content` 302, `?format=pdf` 302 via mediap), not just `/shares` — which is why this shipped as `resolve-drive-share-link` returning `tenantId` + an optional `--tenant-id` on the drive-item family, NOT as a one-shot share-URL download command (that would have failed identically, and only ever covered what you built). One shared RT slot is correct: a guest-rotated RT still refreshes the HOME tenant (verified), so RTs are not tenant-scoped and per-tenant RT chains are unnecessary. Do NOT confuse this with the 2026-07-16 entry below: that one says cross-tenant DIRECTORY resolution (`/users/{home-id}`) is dead, and it still is. Different boundary — identity lookup vs token acquisition.
Rule for next time: on `invalidAudienceUri`, check whose tenant the HOST belongs to before touching scopes or token tiers; the host->onmicrosoft mapping is a CONVENTION (a vanity sign-in domain breaks discovery), so treat a failed discovery as "cannot cross to this tenant" and surface it, never as a crash.

## [decision] 2026-07-16 | `login` re-captures the elevated token itself when it is missing (supersedes the 2026-07-13 "login is a slim confirmation, --force is the mechanism" decision)

The 2026-07-13 entry was right about the mechanism and wrong about the signpost, and the gap was a loop with no exit: a command needing elevated said "run `ask-marcel-office login`"; `login` found a valid cached BASIC token, returned on the cache rung, printed `authenticated` — and never re-captured elevated, which carries no refresh token of its own; the command then failed identically. Forever. The user hit it live. `login.execute` now escalates to `getAccessToken({force:true})` when `getCachedElevatedInfo()` reports elevated unavailable — the SAME rung `--force` uses, deliberately: the browser adapter's `freshCachedToken` probe short-circuits the dance when a valid token is cached and only the forced path suppresses it, so a hand-rolled re-capture would silently no-op (exactly how `--force` itself shipped broken once). An already-forced login does not escalate again, so a tenant whose elevated capture keeps failing gets one browser per invocation, not two. Both halves verified live: elevated missing -> browser opens; elevated present -> no browser, instant. Note the remedy is NOT uniform across the three secondary tiers, though one shared message claimed it was: chatsvcagg/ic3 ride the shared RT and self-heal headlessly, so plain `login` is right for them and `--force` costs a browser they never needed.
Rule for next time: the false absolute ("the only way to refresh...") had propagated to FOUR places (the elevated fail-fast message, `scopes-check`'s hint, `scopes-check`'s summary, the README) and one change falsified all of them at once — when writing a remedy into a message, do not write "the only way" unless you have checked every tier it covers.

## [mistake] 2026-07-16 | Threading a param through commands with a regex missed `graph.get` — a green suite proved the logic, not the assumption, for the FOURTH time

Adding `--tenant-id` to the byte-fetch commands, a scripted edit regexed `fetchRawBytes(` / `inlineBinary(` and threaded the tenant in. It did not match `graph.get(` — so `download-drive-item-as-pdf` and `extract-drive-item-images`, which read the item's METADATA first (to detect a folder / learn the filename), left that read on the home token. For a partner-tenant file the metadata read is the FIRST call, so both failed with `invalidAudienceUri` before the download they were setting up. Every gate was green; the user found it in one live command. The tests were green because they asserted the guest token IS used and never that the home token is NOT — an assertion that cannot see a call it does not know about. `convert-drive-item-zip` escaped only because it has no metadata read at all: luck, not design. Fix: `tenant-routing.test.ts` builds a fake whose `get`/`getBinary`/`getBinaryElevated` THROW, so any unrouted call anywhere in the command explodes; verified by reintroducing the bug (fails) and restoring the fix (passes). Same session, mutation testing caught the two other things no gate could: a narrowing ternary that was pure dead complexity (every `GraphError` variant already carries `message` — 10 survivors deleted with the line, not with a test), and a security test that passed for the WRONG reason (the path-traversal case contained no GUID, so the character classes rejected it whatever the anchors did; both `^` and `$` survived as Regex mutants, and the real attack shape `<valid-guid>/../../evil` was untested).
Rule for next time: when threading a new parameter through N call sites, assert the NEGATIVE (the old path is never taken) with a fake that throws — an assertion that the new path works cannot see the site you missed. And a scripted/regex edit across files needs the same negative guard, because the thing it silently skips is invisible by construction.

## [gotcha] 2026-07-16 | `mutate:changed` cannot see an untracked file, so a NEW file silently skips the mutation gate — and it bases on `origin/main`, so unpushed commits widen its scope

`scripts/mutate-changed.sh` selects via `git diff --name-only <BASE>...HEAD` + `git diff HEAD` + `git diff --cached`. A brand-new, never-`git add`-ed file appears in NONE of those, so `src/domain/tenant-id.ts` was never mutated while the script exited 0 and looked like a pass — every new domain/use-case file this repo has ever added hits this. Stage it first (making it `--cached`), or run `bunx stryker run --mutate <path>` explicitly. Separately, `BASE` defaults to `origin/main`: with local `main` 3 commits ahead it selected `get-user.ts` / `graph-scopes.ts` / `resolve-drive-share-link.ts` — all already committed, none touched that session — and spent 29 minutes mutating them. Use `BASE=HEAD` when iterating with unpushed commits, or push first. Two more traps confirmed this session: Stryker's dry run needs the suite 100% GREEN, so a RED test written for the next slice blocks mutation of the current one; and the sandbox is copied at run START, so a survivor reported against a test file written mid-run is STALE — re-run before believing it (a survivor on `callBinary` looked real and was not).
Affects: every `bun run mutate:changed` / `mutate:staged`; treat a clean run on a new file as unproven until you have seen the file's own name in Stryker's output.

## [gotcha] 2026-06-13 | an additive error-envelope field must be threaded through ALL THREE layers (infra → composition → presenter) or CLI consumers never see it

Surfacing Graph's `Retry-After` as `retryAfterSeconds` required edits in three files, not one: the `api_error` variant of `GraphError` (`src/infra/graph-client.ts` — `parseRetryAfter` reads `res.headers.get('retry-after')`, delta-seconds only, spread into all THREE `apiErrorFrom` return paths), the composition `fail()` wrapper + the per-command error site (`src/composition/cli.ts` — extract `result.error.type === 'api_error' ? result.error.retryAfterSeconds : undefined` and forward it), AND the presenter `renderError` (`src/presenter/output.ts` — add to the JSON envelope and a `retryAfter: Ns` text line). Adding the field to `GraphError` alone reaches *library* consumers (`commands[x].execute` callers) but NOT CLI consumers, because `renderError` takes discrete primitive params, not the whole error object — the same shape the `errorCode` / `hint` / `source` fields already follow. Guard on `!== undefined`, never truthiness: `0` is a valid "retry immediately" hint. The RFC HTTP-date form is intentionally unparsed (needs a clock; Graph uses integer seconds for throttling) — absent/non-numeric → field omitted → caller falls back to its own backoff. ask-marcel-office itself still does NOT retry; the client is fail-fast and the orchestrator owns the backoff loop.
Applies to: any new field on the `{ok, error, errorCode?, hint?, source}` envelope — thread GraphError → cli.ts `fail` → output.ts `renderError`, and document it in docs/USAGE.md (the canonical envelope-shape block) + README.

## [gotcha] 2026-06-13 | `^`-ranged lint toolchain drift can break `bun run lint` on an unchanged HEAD — fix rule severity at project level, never inline

`typescript-eslint` resolving to 8.59 (within the `^8.33.1` range in package.json) began flagging the `_graph` / `_params` parameters on local-only commands' redirect-`execute` (`@typescript-eslint/no-unused-vars` has NO default `argsIgnorePattern`), so lint failed with 2 errors on code that predates the session — a toolchain bump, not a code change. ## [gotcha] 2026-06-02 | the Search index returns non-navigable site TYPES (404s) the archive probe misses — filter by URL shape + a 404 probe

## [mistake] 2026-06-02 | `/tmp/...${Date.now()}.json` temp paths collide across parallel `bun test` processes → flaky

`build-deps.test.ts` seeded a real cache at `/tmp/atelier-build-deps-cache-${Date.now()}.json` and deleted it in `finally`. `Date.now()` (ms) is NOT unique across processes, so when several `bun test` runs overlap (CI shards, a `bun run` racing a background mutation run, or Stryker's own spawned dry-run) two land on the same path in the same millisecond and one's cleanup deletes the other's file mid-read → intermittent single-test failure. It surfaced only under load (0/6 idle runs, 1/4 parallel runs) and BLOCKED Stryker, whose initial dry-run must be 100% green. Fix: `mkdtempSync(join(tmpdir(), 'prefix-'))` for an OS-guaranteed-unique dir (node:fs is allowed in tests per hard rule 20; three infra tests already do this), write inside it, `rmSync(dir, {recursive:true})` in `finally`. To hunt a load-sensitive flake, run N suites in parallel rather than N sequentially.
Applies to: every test that touches a real temp path; never key a shared-filesystem path on `Date.now()` alone.

## [gotcha] 2026-06-02 | Stryker counts `Timeout` mutants as KILLED — manual `mutation.json` parsing must too

A mutant that makes a loop run forever (e.g. `start < n` → `start >= n`, or `start += chunk` → `start -= chunk`) is reported with `status: "Timeout"`, and Stryker's break-threshold math counts Timeout as detected/**killed**. A hand-rolled `mutation.json` parser that only counts `status === "Killed"` (treating Timeout as a survivor) under-reports the score and disagrees with Stryker's own pass/fail — e.g. a real 90.91% read as 89.3%. Trust the `Final mutation score of N` line in Stryker's log; if parsing the JSON, count `Killed` + `Timeout` (and exclude `CompileError`/`NoCoverage` per your gate's intent).
Applies to: any script that parses `reports/mutation/mutation.json` to gate or report mutation score.

## [gotcha] 2026-06-01 | auto-archived OneDrives fail `GET /sites/{id}` with 423 resourceLocked, not 200 + archiveStatus

## [gotcha] 2026-06-01 | the machine-readable mutation report needs the `json` reporter added — `mutation.json` is otherwise stale

`stryker.conf.json` here emits `["clear-text", "progress", "html"]` — NO `json` reporter — so `reports/mutation/mutation.json` is NOT refreshed by a normal run; it retains whatever a prior run left behind, and parsing it (per the 2026-05-30 lesson) then reports STALE survivors as if current. Affects: any scoped or full `bunx stryker run` where you parse `mutation.json` to close the 90% gate.

## [decision] 2026-06-01 | per-document sensitivity labels are unreachable on the Teams token (content scope absent)

Per-document MIP sensitivity labels read via the POST action `/drives/{d}/items/{i}/extractSensitivityLabels` (the `driveItem` resource exposes no GET label field in Graph v1.0). So a per-item label read 403s like the other token-ceiling blocks (`Chat.Read`, `ChannelMessage.Read.All`, …). Spiked during the "full-fidelity document context" feature and DROPPED: the catalog command stays, but `download-drive-item-as-markdown --include-metadata` cannot surface a per-file `**Sensitivity:**` line on this token. ## [gotcha] 2026-05-30 | a "survived" mutant you can't explain is usually an operand-level equivalent — pull the exact id

Under `--force` the cache still held the valid basic token, so the probe short-circuited on the FIRST poll — the browser opened and closed immediately ("Token was refreshed by another process — closing the browser"), capturing nothing; the four-token status then just reflected the stale cache. The force unit test passed because `fakeBrowserAuth.acquireBothTokens` returns its configured result and does NOT model the `freshCachedToken` short-circuit — the fake proved the plumbing, not the behavior. Only a live `login --force` caught it. Fixed by threading a `skipCacheProbe` flag (force -> `acquireViaBrowserShared` -> `acquireViaBrowser` -> `acquireBothTokens`) so the probe is not consulted under force. This is the THIRD fake-vs-real-API miss in one session (create-forward-draft body, then this).
Rule for next time: when a fake stands in for an adapter that has INTERNAL control flow the port type does not express (a poll loop, a cache probe, a retry, a redirect), the fake models your ASSUMPTION of the adapter, not the adapter. Test that branch at the adapter's OWN seam — here `createBrowserAuthFromApi` + a `freshCachedToken` that returns a token, asserting `skipCacheProbe` suppresses the short-circuit — not only through the port fake. And live-smoke any auth-flow change; the browser dance is not observable from unit tests.

## [gotcha] 2026-07-13 | ic3 (and chatsvcagg) substrate bearers are captured only opportunistically at login — ic3 needs a chat-history load the settle window rarely triggers

The login browser dance captures the chatsvcagg / ic3 substrate tokens by watching network traffic for their audience-specific bearers (`aud=https://ic3.teams.office.com` for ic3). chatsvcagg fires from the automatic chat-LIST load on the Teams landing page, so it usually captures; ic3 fires only when Teams loads a chat's MESSAGE history (the IC3 substrate call), which does NOT happen on its own during the brief post-sign-in settle window — then the page navigates to m365.cloud.microsoft for elevated and the chance is gone. So a fresh login routinely leaves ic3 `available:false` even though elevated + chatsvcagg captured. It is NOT broken: `list-teams-chat-history` (the only ic3 consumer) headlessly redeems ic3 from the shared refresh_token on first use (`getIc3AccessToken` -> `refreshSubstrateToken`, no browser), and `login --force` now proactively redeems any missed substrate token from the fresh RT after the dance (`redeemMissedSubstrateAtLogin`) so all four report available.
Rule for next time: do not treat ic3 `available:false` after a plain login as a bug — the browser capture is best-effort; the headless RT redemption is the reliable path. chatsvcagg and ic3 share it (`refreshSubstrateToken`, different resource aud); elevated does NOT (no refresh_token — browser only).

## [decision] 2026-07-13 | scopes-check is the single detailed token-status view; login is a slim auth confirmation (2.2.0)

The four-token status dashboard added to `login` in 2.1.0 was reworked in 2.2.0: `login` slimmed to `{ status: 'authenticated', available: string[], hint }` (which tiers are available + a pointer to `scopes-check` and `login --force`), and the detailed per-token view moved to `scopes-check` — the natural home because it is the ONLY side-effect-free read (pure local decode, no Graph call, no browser) and already listed scopes. This keeps the safe pre-flight (agents check status without risking an auth side-effect) while removing the login/scopes-check overlap. `scopes-check` now reports, per tier, `{ available, expiresInSeconds?, scopes, refresh }` where `scopes` is that token's OWN grant decoded from its `scp` claim: the four tokens carry DISTINCT sets (basic ~31 Graph scopes, elevated ~20 different Graph scopes, chatsvcagg `user_impersonation`, ic3 `Teams.AccessAsUser.All`). Shape is ADDITIVE (flat top-level basic fields unchanged → non-breaking vs 2.0/2.1). The `refresh` marker is a fixed per-tier property assembled in `getCachedTokenInfo` (graph-client); scopes are decoded in the auth-layer `getCached*Info` (they hold the tokens) and flow through `CachedTierInfo`.
Rule for next time: keep `scopes-check` side-effect-free (it is the LLM safe pre-flight) and put token/scope DETAIL there; keep `login` an action that prints only a confirmation. The meta.test summary-flag validator extracts any `--flag` from a registry command's summary and requires it be a real option on THAT command, so do not write another command's flag (e.g. `login --force`) into a registry command's summary — reword (responseShape is exempt).

## [gotcha] 2026-07-15 | Guest / B2B UPNs carry `#EXT#`; a raw `#` in a `/users/{id}` path is silently dropped as the URL fragment — encodeURIComponent the userId

A guest (B2B) user's userPrincipalName is `alice_contoso.com#EXT#@fabrikam.onmicrosoft.com` (home UPN with `@`→`_`, plus the literal `#EXT#` marker, plus the host-tenant domain). The `#` is the URL fragment delimiter, so interpolating a UPN raw into `/users/${userId}` and handing the string to `fetch` drops everything from the first `#` onward — Graph receives `/users/alice_contoso.com` and returns `Request_ResourceNotFound` for the WRONG (truncated) principal. This is invisible to unit tests that only use `@`-style UPNs and to `new URL()` normalization (which percent-encodes query spaces/quotes but CANNOT encode a path `#` — structurally it is already the fragment start). Microsoft's docs are explicit: for B2B UPNs "you must encode the reserved character '#' as '%23' in the request URL". Fixed by wrapping the id segment in `encodeURIComponent` across `get-user` (new) + 7 shipped siblings (`get-user-manager`, `get-shared-mailbox-message`, `list-shared-mailbox-messages`, `list-shared-mailbox-folder-messages`, `list-shared-calendar-events`, `list-user-direct-reports`, `list-shared-calendar-view`). Verified live: `list-user-direct-reports` / `get-user-manager` with a `%40`-encoded real UPN resolved the user and returned data — so `@`→`%40` is accepted by Graph on the wire (the official SDKs encode path params the same way). The name path in `get-user` does NOT need this: its value sits in a `$search="..."` QUERY literal, where `new URL()`/`fetch` percent-encodes spaces and the `"`-strip handles injection; only PATH segments have the `#`-fragment hazard.
Rule for next time: any Graph path segment that can hold a caller-supplied UPN MUST be `encodeURIComponent`'d — a GUID passes through unchanged, `@`→`%40` and `#`→`%23` are both accepted. Guard it with a fixture that feeds `alice_contoso.com#EXT#@fabrikam.onmicrosoft.com` and asserts the path contains `%23EXT%23` and NOT `#EXT#` (doubles as the mutation guard on the `encodeURIComponent` call). `capturedUrl` in commands.test.ts returns the raw pre-fetch string, so the assertion sees the encoding directly. Note the `$`-prefixed-UPN OData caveat (`/users('$foo')`) is a separate, rarer case encodeURIComponent does not solve, but `$` is not a legal UPN character so it does not arise here.

## [mistake] 2026-07-15 | The basic-token refresh OVERWROTE the cache instead of merging, silently wiping the elevated / chatsvcagg / ic3 tokens on every renewal

`refreshToken` (auth.ts) rebuilt the cache as a fresh `{ access_token, expires_on, refresh_token }` and wrote THAT, so every silent basic-token refresh — fired automatically whenever the Teams token neared expiry mid-session — dropped the three secondary tokens. Every other write path (`setElevated` / `setChatsvcagg` / `setIc3`, and the substrate refresh-token rotation) already merged via `{ ...existing, ... }`; `refreshToken` was the lone overwrite. The user surfaced it: `scopes-check` showed elevated/chatsvcagg/ic3 `available:false, scopes:[]` and the on-disk cache held only the three basic keys, even shortly after a `login --force` that had captured all four. Elevated hurt most — it carries no refresh_token of its own, so once wiped it could only return via a forced browser re-login. Fixed by spreading `...cached` FIRST in the refreshToken write object. The pre-existing "refreshes expired token" test only asserted `result.ok`, so it never saw the clobber; the new guard seeds a full four-token cache with the basic token expired, calls `getAccessToken()` (triggers the refresh rung), then reads the cache back and asserts the secondaries + the rotated refresh_token all survive.
Rule for next time: EVERY cache/state write must MERGE (`{ ...existing, <changed fields> }`), never construct a fresh record from a subset of fields — a partial write silently drops sibling data that another code path owns. And when a function mutates-then-returns, a test that asserts only the RETURN value proves nothing about what landed on disk; add one that asserts the PERSISTED side effect. This was a fake-vs-real class of gap in spirit (the test modelled the happy return, not the durable write).

## [decision] 2026-07-15 | get-user-manager's 404-disambiguation `&&` chain carries 7 accepted mutation survivors — a scoped change is not the place to chase them

get-user-manager maps a 404 `Request_ResourceNotFound` that names `Resource 'manager'` to `ok({ manager: null })` (user exists, no manager set) but passes through a 404 that names the userId (user absent). The 4-clause guard — `type === 'api_error' && status === 404 && includes('Request_ResourceNotFound') && includes("Resource 'manager'")` — carries 7 surviving mutants on the FIRST THREE clauses: the tests pin the `'manager'`-vs-userId discrimination (clause 4) but never feed a non-404, a non-`api_error`, or a 404 whose body lacks `Request_ResourceNotFound`, so Stryker deletes those three guards freely and no test fails. They surfaced during the guest-UPN encoding fix (which touched only the path line, not this block), so they are pre-existing and unrelated; the repo mutation gate is an AGGREGATE ≥90 that still passes, so they were flagged for honesty, not chased.
Rule for next time: a scoped change is not the venue to harden an unrelated pre-existing branch — flag the survivors, keep the commit tight, and let the aggregate gate be the bar (same call made for the auth.ts refreshToken plumbing survivors). To kill these when the branch is next genuinely touched: three tests in get-user-manager.test.ts, each asserting err PASS-THROUGH (not `manager: null`) — a 500 `api_error` (kills `status === 404`), a `network_error`/non-`api_error` (kills `type === 'api_error'`), and a 404 whose message omits `Request_ResourceNotFound` (kills that `includes` string).

## [decision] 2026-07-16 | A cross-tenant Teams participant's HOME object id cannot be resolved to a person from your tenant — the guest object retains no link to it (confirmed dead, do not re-attempt)

An external collaborator appears as TWO distinct AAD objects: (1) a GUEST object in your tenant — its own object id, UPN `alias_homeorg#EXT#@yourtenant.onmicrosoft.com`, `mail` = their real home email — fully resolvable by `get-user` (by name, by mail via the mail-eq fallback, or by the guest id); and (2) their NATIVE object id in their HOME tenant, which surfaces in cross-tenant Teams chats as the MRI `8:orgid:<home-id>`. `GET /users/<home-id>` returns `Request_ResourceNotFound` — your directory holds no foreign-tenant objects. The one possible bridge was the guest's `identities` array, and it is empty: for an AAD-to-AAD B2B guest, Graph returns the federated identity as `{ signInType: 'federated', issuer: 'ExternalAzureAD', issuerAssignedId: null }` — the home object id is deliberately withheld (cross-tenant isolation), so `$filter=identities/any(i:i/issuerAssignedId eq '<home-id>')` matches nothing. There is NO directory path home-id ↔ local-guest in either direction, and this generalizes to every B2B guest (not one account). Email can't disambiguate the two objects either — both carry the same `mail`. The person's name lives ONLY in Teams' own chat payload (the sender's embedded imdisplayname), never in the directory.
Rule for next time: do NOT try to resolve a cross-tenant `8:orgid:` MRI or a foreign home object id via Graph `/users` or an `identities`/`issuerAssignedId` filter — it is an Azure AD boundary, confirmed dead this session. To name an external Teams participant, read the display name straight off the chat message/roster payload instead. `get-user` documents the boundary in its summary and in the `Request_ResourceNotFound` hint (error-hints.ts).
