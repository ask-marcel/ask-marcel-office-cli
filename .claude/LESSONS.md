## [mistake] 2026-08-27 | Two real Entra object ids reached a public repo because the fixture was edited down from a diagnostic dump instead of synthesized

While hardening the pptx comment extractor, the identity test in `pptx-comments.test.ts` was built by copying `S::<UPN>::<Entra object id>` triples straight out of a diagnostic dump of a real deck and swapping in `contoso.com` addresses. The email halves were replaced. The GUID halves were not. `5c1a3800-...` and `b83acc04-...` are directory object ids for real people, and they shipped in `e61f1e0` to a public MIT repo, the exact class of string the 2026-07 purge rewrote history to remove. Substituting the obviously-sensitive half of a composite identifier feels like sanitising and reads as sanitised on review, while the other half travels untouched. Nothing caught it: gitleaks does not match bare GUIDs, no test asserted on them, and all 8 gates passed. It surfaced only when a later task revisited the same fixture. Recovery, with `rebase -i` unavailable in the harness: `git stash` the unrelated edit, synthesize the GUIDs, `git reset --soft HEAD~1`, unstage the intervening commit's file, `git commit --amend`, re-commit it, then `git push --force-with-lease`. That cleared every commit reachable from `main`, but left the pre-rewrite commits fetchable by SHA on the host until its GC.
Rule for next time: never derive test data from a dump of real content. Learn the format from the sample, write the format down, then build the fixture from the format. For composite identifiers (`S::a::b`, connection strings, URLs with embedded ids) treat every segment as real until each one has been deliberately replaced, because sanitising only the recognisable half is the failure mode. Before committing, grep the staged diff for any literal that came from a live probe.

## [gotcha] 2026-08-27 | pptx comment authors outlive the comments, so "authors listed, comments empty" is a correct render far more often than a parser bug

A reported deck rendered 8 rows under "Comment authors" and `_(none)_` under "Comments", which reads like a broken extractor. It was not. `ppt/authors.xml` (modern, GUID ids) and `ppt/commentAuthors.xml` (legacy, integer ids) are append-only registries PowerPoint never prunes when a comment is resolved or deleted. A full zip survey settled it: 170 entries, no `ppt/comments/` folder, no comment part in `[Content_Types].xml`, no slide `_rels` pointing at one, and zero `<*:cm>` elements in any XML part of the package. The legacy author even carried `lastIdx="1"`, proving a comment had existed and was later removed. The deck also carried `ppt/changesInfos/` plus WPS Office tags (`KSO_WM_BEAUTIFY_FLAG`) and think-cell, so a non-PowerPoint round-trip dropping the p188 parts is the likely history. Separately, both registries carry the commenter's directory identity in `userId` as `S::<UPN>::<Entra object id>`, on the modern `<author>` element directly but on the legacy `<cmAuthor>` only inside a `<p15:presenceInfo>` nested under `extLst > ext`; that is now the `email` column.
Rule for next time: before touching the comment extractor, list the zip entries. Presence in the author registry proves someone commented once, never that a comment is still in the file. Diagnose from `ppt/comments/` plus a grep for `<*:cm>` across every part, and report "the file has no comments" rather than hunting a parsing bug that is not there.

## [decision] 2026-08-27 | XML local-name matching is scoped to pptx comments; docx keeps the qualified match

An XML namespace prefix is a per-document alias for a namespace URI, not part of the schema, so `findAll(root, 'p188:cm')` silently returns nothing for a deck whose writer bound that URI to its own prefix. `ooxml-xml-walker.ts` now exposes `findAllLocal` and `collectTextLocal` beside the qualified `findAll` / `collectText`, sharing one walk through internal matchers, and `pptx-comments.ts` keys on the local names `cmAuthor`, `author`, `cm`, `text`, `t`. Making the walkers local-name-only across the board was rejected: `docx-metadata.ts` collects `w:t` for paragraph text, and a docx containing a drawing also carries `a:t`, so prefix-blind matching there would fold shape text into paragraph text. Because both comment generations share the local name `cm`, the legacy and modern passes collapsed into one: the date falls through `dt` to `created`, the body through `text` to `t`. Shipped in `e61f1e0`.
Rule for next time: reach for the local-name walkers only where the local name is unambiguous inside the part being read, and name the collision the qualified match is protecting when leaving a caller on it.

## [gotcha] 2026-08-27 | `mutate:changed` diffs against the LOCAL `origin/main` ref, so a missing fetch makes old commits look unpushed

`scripts/mutate-changed.sh` defaults `BASE=origin/main` and intersects that diff with the mutation scope. Against a stale remote-tracking ref it listed `get-user.ts`, `update-mail-draft.ts`, `create-reply-draft.ts` and others alongside the two files actually under change, which was read as evidence that `main` carried several unpushed commits and that a push would send them all. A `git fetch origin` settled it: `origin/main..HEAD` held exactly one commit, 0 behind and 1 ahead. The extra files were older commits the stale ref had not caught up with. Worse, `git status --short --branch` prints no ahead/behind bracket in that state, so it corroborates the wrong reading instead of correcting it.
Rule for next time: `git fetch` before treating any `origin/main`-relative output as a statement about what is unpushed, and confirm push scope with `git log --oneline origin/main..HEAD` after the fetch rather than inferring it from a mutation or diff file list.

## [mistake] 2026-07-17 | A long-lived worktree branch silently diverged from main, so main's FIXES looked like drift — and merging it would have re-published a purged real email

The MCP work was built in a `.claude/worktrees/` branch assumed to be a recent cut of `main`. It was not: it forked at `d19de64`, and both sides then advanced ~290 commits. Because the 2026-07 privacy purge rewrote history, most of those commits are the SAME work under different SHAs, which makes the commit graph useless for judging drift — `git rev-list --count` said "292 ahead / 294 behind" while the real content delta was ~40 files. Two costly misreadings followed. (1) The branch's `docs/COMMANDS.md` said "All 182 commands" against a 183-command registry, so a `[mistake]` entry was drafted accusing the repo of shipping commands without running `docs:gen`. FALSE: `main` already carried `b954b57 docs(mail): regenerate manifest…` and already said 183. The staleness was the BRANCH lacking main's commit, not the repo skipping a step — and nothing visible on the branch could reveal that; only `git show main:docs/COMMANDS.md` could. (2) Far worse, the pre-purge branch still contained `Loewe` (8 sites), `lvmh`, and a real person's real email address in `get-user.test.ts` — all scrubbed on `main` by `6364ec3 fix(privacy): replace client vocabulary…`. Merging or rebasing that branch would have re-published them to a public MIT repo whose history was force-pushed specifically to remove them. Verified contained: the branch was never pushed, `origin` holds only `main`, and `origin/main` is clean. The fix was to cherry-pick the 11 MCP commits onto a fresh branch off `origin/main` (they applied cleanly except the generated docs and a structurally-rewritten README) and REGENERATE `docs/commands.json` on the clean base, which dropped the branch-local `Concur` an earlier regen had propagated into it.
Rule for next time: never assume a worktree or feature branch is a recent cut of main — run `git merge-base HEAD main` and `git diff main HEAD --stat` BEFORE starting, and diff against `main:<path>` before concluding that anything is stale, missing, or wrong. After a history rewrite, commit counts between branches are meaningless; only content diffs are. Treat any branch predating the purge as radioactive: extract work by cherry-picking onto `origin/main`, never merge or rebase it back, and regenerate generated files on the clean base rather than carrying them across.

## [gotcha] 2026-07-17 | The MCP `login` tool takes 37-64s with NO MFA and the MCP default tool timeout is 60s — it times out intermittently, right on the boundary

The ADR anticipated that an MFA-length FIRST login could outlive an MCP client's tool-call timeout, and documented first-run as terminal-first on that basis. Live measurement against the real tenant showed the problem is bigger: the ORDINARY case — silent SSO, no MFA prompt, persistent profile already authenticated — measured **63.9 s**, then **36.8 s**, then a clean **60.0 s timeout** (`McpError -32001`). Duration swings with how warm the Playwright persistent profile is. The SDK's `DEFAULT_REQUEST_TIMEOUT_MSEC` is **60_000** (`node_modules/@modelcontextprotocol/sdk/dist/esm/shared/protocol.js:8`, applied per-request at `:712` as `options?.timeout ?? DEFAULT_REQUEST_TIMEOUT_MSEC`), so `login` sits exactly on the boundary and fails intermittently — the worst failure shape, because it works when you test it and fails for the user. NONE of this is visible to `mcp.test.ts`: the auth fake returns instantly, so the unit test measures nothing about the real browser dance. Mitigation shipped as docs + the tool's own `description` (which the model reads): raise `MCP_TOOL_TIMEOUT` to ~300_000. Also established: the stdio server SURVIVES a client-side request timeout and keeps serving later calls, so a timed-out sign-in has usually still completed — but only if the client merely times out the request; if it CLOSES the transport, `StdioClientTransport` kills the subprocess and the login is genuinely lost (a probe that called `client.close()` in its catch conflated the two and wrongly showed "timed out AND no tokens").
Rule for next time: for any MCP tool that wraps a slow real-world action (a browser dance, a big conversion, a deep paging sweep), MEASURE it live and compare against the 60 s SDK default before shipping — a fake makes every tool look instant. When a duration lands near a timeout boundary, treat it as broken, not borderline. And when probing timeout behaviour, do not tear down the transport in the catch: you will measure your own teardown instead of the server.

## [gotcha] 2026-07-17 | An MCP stdio server's stdout purity is invisible to BOTH the unit tests AND a Client-based handshake — only a raw-stdout assertion catches a stray write

Under MCP stdio, stdout IS the JSON-RPC frame channel: one `process.stdout.write` (an update-notifier banner, a debug print, a stray log) corrupts the stream. Two obvious guards both fail to see it. (1) `mcp.test.ts` drives `InMemoryTransport.createLinkedPair()`, which never touches stdout at all — protocol corruption is invisible there BY CONSTRUCTION, not by oversight. (2) Less obviously, a real stdio handshake through the SDK's own `Client` ALSO passes: injecting `process.stdout.write('STRAY BANNER\n')` into the `mcp` path produced a bundle whose raw stdout was literally `STRAY BANNER\n{"result":...}`, and a `StdioClientTransport` + `Client` probe still reported a clean 5-tool handshake — the SDK's `ReadBuffer` silently SKIPS lines it cannot parse, so a tolerant client hides the exact bug the gate exists to find. The spec says the server MUST NOT write non-MCP output to stdout; a stricter client, or a future SDK that stops skipping, drops the session. The working gate spawns the built `dist/cli.js` directly, feeds a raw `initialize` + `tools/list`, and asserts EVERY non-empty stdout line parses as JSON with `jsonrpc === '2.0'` (`scripts/qa-bundle-smoke.ts` `probeMcp`). Verified in both directions: fails the injected bundle naming the polluting line, passes the real one. A second guard is an ESLint `no-restricted-properties` block banning `process.stdout` in `src/composition/mcp.ts` ONLY — note the naive rule "ban it outside `presenter/output.ts`" is WRONG here and would break `cli.ts:60,227`, which legitimately own stdout in CLI mode.
Rule for next time: never accept a green handshake as proof that a stdio server's stdout is clean — assert on the RAW bytes. More generally, when a client library is tolerant of malformed input, a test built on that client cannot detect the malformation; drop to the wire. And prove any new guard fails on a deliberately injected violation before trusting it.

## [gotcha] 2026-07-17 | Workflow subagents share the working tree — one reverted the parent session's `bun add` while `git status` read clean

A 13-agent design-review workflow ran against this repo while the parent session worked in the same worktree. A subagent probing "is the MCP SDK installed?" ran `bun add @modelcontextprotocol/sdk`, then `git checkout`-ed `package.json` to leave the tree tidy — which ALSO reverted the parent session's real, intentional install minutes earlier. The end state was the trap: `node_modules/@modelcontextprotocol/sdk@1.29.0` physically present, `package.json` with no such dependency, and `git status` completely clean. Every import resolved locally, so nothing failed until a fresh `bun install` on another machine would have. The workflow's own report flagged it as "a prior probe auto-installed it and the dep was reverted but the tree wasn't", which read as a pre-existing repo condition rather than as damage the workflow itself had just done. This is the 2026-06-23 lessons.local entry (parallel Claude sessions collide silently) with a new colliding writer: your OWN subagents. Related trap in the same session: `bun add` rewrote the `description` field, unescaping `—` to a literal em dash — an unrelated drive-by change that had to be restored to keep the diff surgical.
Rule for next time: subagents are not read-only just because you asked a read-only question — they run package managers and git. After any workflow whose agents could mutate the tree, re-verify state (`git status`, `git diff package.json`) before trusting it, and re-do anything you did concurrently. Prefer `isolation: 'worktree'` for agents that might write. And after every `bun add`, check `git diff package.json` for collateral reformatting, not just the dependency line.

## [gotcha] 2026-07-17 | An adversarial multi-agent review's ARCHITECTURE held up while its ARITHMETIC did not — verify every count against the registry

A 13-agent review (2 skeptics per finding, 3 competing designs, 3 judges, ~1M tokens) produced genuinely load-bearing architectural work: it killed two of three proposed findings as overstated, caught that `renderTextOutput`/`findErrorHint` were already pure (shrinking the planned extraction), and empirically reproduced two fatal blockers in the "drive commander from MCP" design (the program object is single-use — `cli.ts` `outputSeen` never resets and `noRepeatParser` compares against the prior parse; and Commander's `_exit` calls `process.exit` when `exitOverride` doesn't throw, so a model passing `--help` kills the server mid-request). All of that survived checking. Its NUMBERS did not: it reported 92 paginating commands (real: 88) and 7 alias-bearing commands (real: 4), each stated with the same confidence as the architecture. It also correctly caught that the ADR's own "182 commands / 3 mutating" was stale (real: 183 / 4). A one-line `bun -e` over the registry settled all of them in seconds.
Rule for next time: agent review output is two different reliability classes in one document. Reasoning about code you can re-derive is worth trusting after a spot-check; counts, percentages, and inventories are worth re-measuring every time, because they are cheap to verify and expensive to be wrong about (they end up hardcoded in a description string a model reads). Measure, then derive from the registry so the number cannot be wrong twice.

## [gotcha] 2026-07-17 | The size gate and the mutation gate pull in OPPOSITE directions — the escape is landing test-only commits FIRST against already-shipped code

Gate 1 caps a commit at 300 lines (insertions + deletions); gate 8 requires >=90% mutation on the staged use-case files. A feature whose tests are what earn the score cannot satisfy both: `get-mail-signature`'s logo embedding was 332 lines because every test was load-bearing (measured — deferring ANY of them dropped the aggregate below the 141 kills it needed, so there was nothing to trim). Splitting code from tests fails the mutation gate instead; the tests cover code the SAME commit stages, and staging a file drags its WHOLE mutant surface in, not just the diff. The way out: land the tests as their own `test(...)` commit FIRST, written against the code as it is already shipped, then the feature commit is small enough. That is why C9 became four commits (convert's debt -> scan/envelope tests -> embedding -> a meta fix) instead of one, and every one passed both gates. The enabling trick is a path BUILDER in the test (`const bodyOf = (id) => ...`): the pre-commit tests pin today's URL, and the feature commit changes that URL in ONE line instead of thirty.
Corollary learned the hard way: DON'T reformat to hit the size gate. Prettier-collapsing fixtures moved 337 -> 332 because the gate counts deletions too, so rewriting lines that already exist in HEAD costs DOUBLE. Densifying a file that partly exists is self-defeating; split the commit instead.
Also: `check-commit-size.sh` counts insertions + deletions. Reading only the insertion count is how C4 shipped at 304 (the hook is inert in this clone — `core.hooksPath` unset — so nothing catches it but you).

## [mistake] 2026-07-17 | Blamed a concurrent session for a draft the USER deleted — the salient anomaly is not automatically the cause

Mid live-smoke, a draft `get-mail-message` had read seconds earlier vanished from Drafts AND Deleted Items. There WAS a concurrent Claude session on the machine doing dramatic things (it rebased this repo's history under me, ran its own privacy purge, untracked `.claude/PLAN.md`), so I attributed the deletion to it, wrote that into the plan file as a finding, and reported it. ## [gotcha] 2026-07-17 | Graph does NOT always emit `appendonsend` — `QUOTE_BOUNDARIES`' marker families are load-bearing, not redundancy. Live-proven: Exchange SafeHTML preserves `divRplyFwdMsg` across a PATCH

Live smoke of the mail-draft splice against a real mailbox: `POST /createReplyAll` returned a draft carrying `divRplyFwdMsg` and NO `appendonsend` at all. The design doc assumed `appendonsend` PRECEDES `divRplyFwdMsg` (the "type above this line" marker; C1's own fixture encodes that order) and described the three marker families in `mail-quote-stripper.ts` as "boundary redundancy" mitigating SafeHTML risk. They are not redundancy — they are the mechanism. An implementation keyed on `appendonsend` alone finds no boundary, and every `--comment` revise refuses with "no quoted reply history". Never collapse `QUOTE_BOUNDARIES` to one family, and never trust a marker's presence from one tenant's sample; `findQuoteBoundary` takes the EARLIEST of whatever is actually there, which is exactly why this passed.
The main external risk is now DISPROVEN, and it needed a real mailbox to do it: Exchange SafeHTML round-trips `divRplyFwdMsg` through `PATCH /me/messages/{id}` unharmed. Proof is the idempotency run, not the create: three PATCHes, comment counts 1/0/0 -> 0/1/0 -> 0/0/1 (each `--comment` REPLACES, never stacks), `divRplyFwdMsg` present after every one, body length stable at ~18.9K. `<head><style>`, the quoted From/Sent block, and raw `<b>`/`&amp;` all survived (not escaped). Forward path identical. Every offline gate had passed against fakes that model our ASSUMPTION of Graph — none of them could have caught a SafeHTML rewrite.
Supersedes one claim in the Stryker entry below: it says `convert-mail-to-markdown.ts`'s 34 survivors were "mostly inert meta-block prose". That was a guess and it was WRONG — 0 of 34 were in the meta block; all 34 were real code (the three ways `fetchInlineImageBytes` abandons one image, each conjunct of `isInlineImage`, the attachments-list failure note). 11 tests killed 8 of them and took the file 88.24 -> 91.00. Do not dismiss a survivor set as inert without reading it: the excuse that a file "can't" be improved was one grep away from being falsified.
Also live: `--reply-all false` -> 1 recipient vs 7 to + 2 cc by default; `--cc-recipients ""` -> cc 2 -> 0 with toRecipients untouched; `get-mail-signature` -> a real 2135-byte block. NOT exercised live: the logo embedding (`inlinedImages: 0` — that mailbox's signature carries no cid: image), so C9b's embed/oversize/note paths remain fake-only.

## [gotcha] 2026-07-17 | Stryker's incremental cache reports STALE survivors when only the TEST file changed — and the aggregate gate makes a low-scoring file un-touchable

`stryker.conf.json` sets `incremental: true` + `incrementalFile: reports/stryker-incremental.json`. The cache keys on the SOURCE file: add tests for existing code, re-run `mutate:changed`/`mutate:staged`/`--mutate <path>`, and Stryker replays the cached verdicts and prints a score that has never seen the new tests. `get-mail-signature.ts` read 86.67% twice in a row across two rounds of new tests (identical to the digit — the tell), then 91.33% the instant `rm -f reports/stryker-incremental.json` preceded the run. Nearly concluded the tests were worthless and went hunting for a design fix to a measurement bug. ALWAYS `rm -f reports/stryker-incremental.json` before a run whose point is to measure NEW TESTS against UNCHANGED source; an identical score across a round of test-writing is the signature, not a coincidence.
Second half, same session: the break threshold is evaluated on the AGGREGATE over the staged set, so a file's own debt becomes everyone's. `convert-mail-to-markdown.ts` sits at 88.24% ALONE (34 survivors / 289 mutants, mostly inert meta-block prose) and had never been imported by another command, so it had only ever been staged next to higher-scoring siblings — invisible debt. Widening its export by THREE LINES for `get-mail-signature` dragged all 289 mutants into the gate and put the aggregate at 84.51%: the arithmetic then demanded 93.4% from the new file just to break even, and NO amount of testing the new code would have cleared it if the new file were small. It worked here only because get-mail-signature.ts is 150 mutants and went to 95.33%. A small file touching that one cannot pass at all.
Rule for next time: before touching a file you have not measured, run `bunx stryker run --mutate <that-file>` ALONE (cache cleared) and learn its solo score — if it is under 90, either raise it first in its own commit or expect to carry it. And when a gate fails, score YOUR file alone before redesigning: it separates your debt from the debt you inherited, which is a different conversation with a different fix.

## [decision] 2026-07-16 | A file in a tenant you are a GUEST in is readable via a guest token redeemed from the shared refresh token against THAT tenant's authority

`401 invalidAudienceUri: Invalid audience Uri '00000003-0000-0ff1-ce00-000000000000'` (SharePoint Online's app id) on a partner tenant's sharing URL is the TENANT boundary, and nothing else. Live-probed, all four combinations: it is NOT scopes (basic and elevated carry identical `Files.ReadWrite.All` + `Sites.ReadWrite.All`), NOT the ODSP appid allow-list (elevated fails identically to basic — do not reach for `getBinaryElevated` here, the 2026-05-06 reflex is wrong for this error), and NOT a missing `Prefer: redeemSharingLink`. Home-tenant Graph simply cannot mint an SPO token for a foreign tenant. The fix: derive the tenant from the URL host (`contoso.sharepoint.com` -> strip `-my` -> `contoso.onmicrosoft.com` -> that tenant's PUBLIC OIDC discovery doc -> tid), then redeem the shared FOCI refresh_token against `login.microsoftonline.com/{tid}/oauth2/v2.0/token`. `Origin: https://teams.microsoft.com` is MANDATORY — the Teams client is an SPA registration and Entra rejects SPA RT redemption that is not cross-origin with `AADSTS9002327`, BEFORE evaluating the grant, so its absence reads as "the tenant refused you" and will send you down the wrong path (it made the first probe report "cross-tenant is impossible"). The guest token reads that tenant's WHOLE `/drives` surface (metadata 200, `/content` 302, `?format=pdf` 302 via mediap), not just `/shares` — which is why this shipped as `resolve-drive-share-link` returning `tenantId` + an optional `--tenant-id` on the drive-item family, NOT as a one-shot share-URL download command (that would have failed identically, and only ever covered what you built). One shared RT slot is correct: a guest-rotated RT still refreshes the HOME tenant (verified), so RTs are not tenant-scoped and per-tenant RT chains are unnecessary. Do NOT confuse this with the 2026-07-16 entry below: that one says cross-tenant DIRECTORY resolution (`/users/{home-id}`) is dead, and it still is. Different boundary — identity lookup vs token acquisition.
Rule for next time: on `invalidAudienceUri`, check whose tenant the HOST belongs to before touching scopes or token tiers; the host->onmicrosoft mapping is a CONVENTION (a vanity sign-in domain breaks discovery), so treat a failed discovery as "cannot cross to this tenant" and surface it, never as a crash.

## [decision] 2026-07-16 | `login` re-captures the elevated token itself when it is missing (supersedes the 2026-07-13 "login is a slim confirmation, --force is the mechanism" decision)

The 2026-07-13 entry was right about the mechanism and wrong about the signpost, and the gap was a loop with no exit: a command needing elevated said "run `ask-marcel-office login`"; `login` found a valid cached BASIC token, returned on the cache rung, printed `authenticated` — and never re-captured elevated, which carries no refresh token of its own; the command then failed identically. Forever. The user hit it live. `login.execute` now escalates to `getAccessToken({force:true})` when `getCachedElevatedInfo()` reports elevated unavailable — the SAME rung `--force` uses, deliberately: the browser adapter's `freshCachedToken` probe short-circuits the dance when a valid token is cached and only the forced path suppresses it, so a hand-rolled re-capture would silently no-op (exactly how `--force` itself shipped broken once). An already-forced login does not escalate again, so a tenant whose elevated capture keeps failing gets one browser per invocation, not two. Both halves verified live: elevated missing -> browser opens; elevated present -> no browser, instant. Note the remedy is NOT uniform across the three secondary tiers, though one shared message claimed it was: chatsvcagg/ic3 ride the shared RT and self-heal headlessly, so plain `login` is right for them and `--force` costs a browser they never needed.
Rule for next time: the false absolute ("the only way to refresh...") had propagated to FOUR places (the elevated fail-fast message, `scopes-check`'s hint, `scopes-check`'s summary, the README) and one change falsified all of them at once — when writing a remedy into a message, do not write "the only way" unless you have checked every tier it covers.

## [mistake] 2026-07-16 | Threading a param through commands with a regex missed `graph.get` — a green suite proved the logic, not the assumption, for the FOURTH time

Adding `--tenant-id` to the byte-fetch commands, a scripted edit regexed `fetchRawBytes(` / `inlineBinary(` and threaded the tenant in. It did not match `graph.get(` — so `download-drive-item-as-pdf` and `extract-drive-item-images`, which read the item's METADATA first (to detect a folder / learn the filename), left that read on the home token. For a partner-tenant file the metadata read is the FIRST call, so both failed with `invalidAudienceUri` before the download they were setting up. Every gate was green; the user found it in one live command. The tests were green because they asserted the guest token IS used and never that the home token is NOT — an assertion that cannot see a call it does not know about. `convert-drive-item-zip` escaped only because it has no metadata read at all: luck, not design. Fix: `tenant-routing.test.ts` builds a fake whose `get`/`getBinary`/`getBinaryElevated` THROW, so any unrouted call anywhere in the command explodes; verified by reintroducing the bug (fails) and restoring the fix (passes). Same session, mutation testing caught the two other things no gate could: a narrowing ternary that was pure dead complexity (every `GraphError` variant already carries `message` — 10 survivors deleted with the line, not with a test), and a security test that passed for the WRONG reason (the path-traversal case contained no GUID, so the character classes rejected it whatever the anchors did; both `^` and `$` survived as Regex mutants, and the real attack shape `<valid-guid>/../../evil` was untested).
Rule for next time: when threading a new parameter through N call sites, assert the NEGATIVE (the old path is never taken) with a fake that throws — an assertion that the new path works cannot see the site you missed. And a scripted/regex edit across files needs the same negative guard, because the thing it silently skips is invisible by construction.

## [decision] 2026-07-16 | `AuthManager` fakes go through `src/test-helpers/auth-manager-fake.ts` — the 2026-06-15 GraphClient rule applies to it verbatim

Adding one method to `AuthManager` broke 29 full inline literal fakes across 5 test files at once (TS2741 everywhere) — the exact situation the 2026-06-15 entry describes, which already named "GraphClient **or a similarly widely-faked port**". The remedy shipped for GraphClient and was never applied here. `fakeAuthManager(overrides?)` mirrors `fakeGraphClient`: quiet defaults (a usable basic token, every secondary tier cancelled), overrides for what a test actually cares about. ## [gotcha] 2026-06-02 | Stryker counts `Timeout` mutants as KILLED — manual `mutation.json` parsing must too

## [gotcha] 2026-05-30 | a "survived" mutant you can't explain is usually an operand-level equivalent — pull the exact id

## [gotcha] 2026-07-15 | Guest / B2B UPNs carry `#EXT#`; a raw `#` in a `/users/{id}` path is silently dropped as the URL fragment — encodeURIComponent the userId

The name path in `get-user` does NOT need this: its value sits in a `$search="..."` QUERY literal, where `new URL()`/`fetch` percent-encodes spaces and the `"`-strip handles injection; only PATH segments have the `#`-fragment hazard.
Rule for next time: any Graph path segment that can hold a caller-supplied UPN MUST be `encodeURIComponent`'d — a GUID passes through unchanged, `@`→`%40` and `#`→`%23` are both accepted. Guard it with a fixture that feeds `alice_contoso.com#EXT#@fabrikam.onmicrosoft.com` and asserts the path contains `%23EXT%23` and NOT `#EXT#` (doubles as the mutation guard on the `encodeURIComponent` call). `capturedUrl` in commands.test.ts returns the raw pre-fetch string, so the assertion sees the encoding directly. Rule for next time: do NOT try to resolve a cross-tenant `8:orgid:` MRI or a foreign home object id via Graph `/users` or an `identities`/`issuerAssignedId` filter — it is an Azure AD boundary, confirmed dead this session. To name an external Teams participant, read the display name straight off the chat message/roster payload instead. `get-user` documents the boundary in its summary and in the `Request_ResourceNotFound` hint (error-hints.ts).

## [gotcha] 2026-07-19 | Chinese Outlook web clients split a quoted header's label and colon into two bold runs — the stripper's label regex must cross inline tags, not just whitespace

A quoted reply-header label and its colon can land in SEPARATE bold runs when the client styles them differently: a Chinese Outlook web client emits `<b><span …>发件人</span></b><b><span lang=EN-HK …>:</span></b>` (label in one `<b>`, colon in the next). mail-quote-stripper's HTML_FROM_LABEL / HTML_SENT_LABEL only tolerated `(?:\s|&nbsp;)*` between the label word and `[:：]`, so the `</span></b><b><span …>` seam broke the match, the topmost quoted message escaped `confirmedHeaderIndex`, and one full quote level leaked past the strip marker (the marker still appeared, proving a LOWER boundary was found — the top one was missed). Distinct from the 2026-07-16 turndown split-bold-run fix (that merged `</b><b>` in the markdown OUTPUT so `**发件人:**` renders clean; this is the quote-BOUNDARY detector on the HTML input). Fixed with LABEL_COLON_GAP = `(?:\s|&nbsp;|</span>|</b>|</strong>|<span[^>]*>|<(?:b|strong)[^>]*>)*` between label and colon in both regexes. Safe because every alternative is a tag/whitespace token, so the run stops at the first real-text char — a bolded word followed by prose never reaches a later colon, keeping the From + (Sent|Date) false-positive guard intact.
Rule for next time: when matching a styled label inside Outlook/Word HTML, never assume the label and its punctuation share one run — a differently-styled colon splits off into its own `<b>`. Tolerate inline open/close tags between them, but bound the alternatives to tag/whitespace tokens so the pattern cannot swallow real text. Test with a fixture where label and colon are separate bold runs.

## [gotcha] 2026-07-19 | Outlook draws its reply divider in TWO standard hues — #E1E1E1 (desktop Word renderer) and #B5C4DF (Mac / mobile) — both must be in QUOTE_BOUNDARIES

The quote-stripper recognizes the Outlook reply divider by its top-border color: `<div style="…border-top:solid #E1E1E1 1.0pt…">`. Only #E1E1E1 (the desktop Word renderer hue) was listed, so a reply whose chain was wrapped by the Outlook-for-Mac / mobile divider (#B5C4DF) was not cut on the divider at all — in the reported message it survived only because the header-label pair (also broken, see the split-run gotcha above) was the last remaining signal, and that was failing too, so the whole quote leaked. Either the divider fix or the header-label fix alone catches the reported message; both together cover header-less divider styles and divider-less header-only replies respectively.
Rule for next time: the Outlook reply divider hue is client-dependent, not locale-dependent — #E1E1E1 desktop, #B5C4DF Mac/mobile. If a new client's quoted chain is not being stripped and it uses a plain `border-top` divider, inspect the hex and add it to QUOTE_BOUNDARIES; cover the new hue with an it.each divider test so the mutation gate pins it (a bare `\s*`→`\S*` regex-flag mutant on that line is an accepted equivalent, since real Outlook writes `border-top:solid` with no space).

## [gotcha] 2026-07-19 | Headless AND headed standalone elevated re-capture hit the sign-in wall on this tenant; a warm token cache is not a warm browser profile

## [decision] 2026-07-23 | Guidance strings are derived from the command manifest and the calling surface, never written as universal claims

The oversized-response banner promised `--output-path` as a "universal remedy (works on every command)". It was false twice over: plain-JSON commands refuse the flag, and the two commands that trip the 50 KB threshold most often (`search-all-files`, `microsoft-search-query`) advertise only `--query`, so the banner's other two levers (`--select`, `--top`) were dead ends there as well. Every remedy it named was unusable on the commands printing it, and an agentic caller that follows printed hints literally burned a call per encounter. `buildSizeHint` now takes an optional `SizeHintContext` (`commandName`, `producesBytes`, `supportsSelect`, `supportsTop`, `surface`) built in composition from `meta.producesBytes` and `meta.options`, so a new command inherits an honest banner with no extra work. Surface matters as much as command: the same `renderToString` serves the CLI and the MCP gateway, an MCP client has no shell (so a redirect recommendation is a fresh dead end) and reaches the flag as an `outputPath` tool param rather than `--output-path`. The `--output-path` rejection in `run-registry-command` carries the same `surface` for the same reason. Renders with no command behind them (the 548 KB `list-commands` manifest, a login summary, a logout status) omit the context and claim no flag-level remedy at all. Rejected: keeping the wording static and fixing only the `--output-path` sentence (leaves `--select`/`--top` lying on the same commands); letting the presenter import the command registry (drags a use-cases concrete into the presenter, where only a type-only `Logger` import crosses today); passing `CommandMeta` wholesale (couples the presenter to a shape it does not need).
Rule for next time: a user-facing hint that names a flag must be able to prove the flag exists on that command and works on that surface. If the string cannot check, it must not claim. Two questions before writing one: which command produced this, and can this caller even type a flag?

## [decision] 2026-07-23 | `--comment` is the one name for above-the-quote text; a whole-body replace on a threaded draft is refused, not warned

`--body-content` meant "the text above the quote" on create-reply-draft / create-forward-draft and "replace the ENTIRE body, quote included" on update-mail-draft. One flag name, sibling commands, opposite blast radius: a caller who learned it on the create command and reused it on update silently wiped the quoted history, and the loss only surfaced if the draft was re-rendered later. Two separate fixes, because the alias alone does not stop the wipe (the confused caller still types `--body-content` on update). First, the guard: update-mail-draft reads the draft before a whole-body replace and refuses when it still carries a quote, which is the mirror image of the existing `noQuoteRefusal` that already refuses `--comment` on a draft with nothing to sit above. `--replace-quoted-history true` is the escape for the legitimate "strip the thread, keep the threading" case, and it skips the read so the deliberate path costs nothing. The same read makes both paths refuse non-drafts with the CLI's message instead of Graph's. Second, the naming: `--comment` is canonical on both create commands (it is Graph's own createReply/createForward payload field, and update-mail-draft's existing word), with `--body-content` kept as an accepted alias. `--body-content-type` deliberately keeps its name, since update-mail-draft pairs that same flag with `--comment`. Rejected: a post-hoc `warning` field in the success envelope (the quote is already gone by the time it is read); refusing with no escape (removes a real capability, since deleting and recreating the draft loses the threading); an alias-only fix matching the report verbatim (retrains nobody, because an alias absent from `--help` is never taught). Consequence worth remembering: `toFailure` rewrites a canonical flag name into whichever alias the caller typed, across the whole message, so an error string that mentions ANOTHER command's flag gets mangled. The two draft-body-unreadable messages therefore name no flag at all and point at `docs update-mail-draft`.
Rule for next time: when one flag name carries two meanings across sibling commands, fix the destructive side first and the vocabulary second; they are different bugs. And never embed a second command's flag name in an error message that passes through the alias rewriter.

## [gotcha] 2026-07-23 | Graph reads a SATISFIED `$top` on mail delta as "sync complete" and hands back a deltaToken; the honoured-OData set differs per delta endpoint and must be probed, not assumed

`list-mail-folder-messages-delta --top 2` on a 67-message Inbox returned 2 messages and an `@odata.deltaLink` (a `$deltatoken`, NOT a `$skiptoken`); following that cursor returned 0, so the other 65 were never delivered and the caller banked a delta token certifying a sync that never happened. This is worse than truncation: a truncated page is visibly short, whereas a premature deltaLink is the protocol's own "you are fully synced" signal, so the loss is silent and the next incremental run inherits it. The cause is not "delta truncates on `$top`" but that Graph treats a satisfied `$top` as the query being complete; the same bound sent as `Prefer: odata.maxpagesize=N` pages normally with a `nextLink`. The second half of the lesson is that the delta family does NOT share one OData rule, and the code comments generalizing from the calendar endpoints were wrong for the others. Probed live: on message delta `$select` / `$filter` / `$expand` are honoured (a future-dated `$filter` returned 0 items instead of 10; `--expand attachments` returned 750 KB), `$skip` is silently ignored (`--skip 5` returned the same first message), `$orderby` hard-fails with `ErrorInvalidUrlQuery` unless it merely restates the default `receivedDateTime desc`. On driveItem delta (`get-drive-delta`, `get-drive-root-delta`) the split is different again: `$top` IS a genuine page size (returns `nextLink` + `@microsoft.graph.hasMoreData`), while `$filter` and `$orderby` are both silently dropped. Fixed by translating `--top` to the header on mail delta and withdrawing each ignored flag on all three commands, with a refusal that states what the probe showed rather than a silent Zod strip (`.strict()` is unavailable on any command carrying a flag alias, because the alias normalizer leaves both the alias key and the canonical key in the params bag).
Rule for next time: before exposing an OData passthrough on a delta endpoint, probe THAT endpoint. Cheap probes that settle it: a predicate matching nothing (honoured returns 0 items, ignored returns the full page), an offset (compare the first item's id), and a page-size bound (`nextLink` means a real page size, `deltaLink` on the first page means the flag just ended your sync). A flag Graph ignores is worse than a missing flag, because the response looks like it obeyed.

## [decision] 2026-07-24 | One name per flag and per command; unknown parameters are refused identically on CLI, MCP, and library

All 77 flag aliases (51x `--id`, 7x `--start`, 7x `--end`, 12 specific) and all 4 `commandAliases` are removed, and an undeclared parameter is now refused on every surface. Two problems drove it. First, the same spelling meant different things across sibling commands, which is how `--body-content` came to mean "text above the quote" on the create-draft commands and "replace the entire body" on update-mail-draft (a data-loss bug fixed the day before). Second, and worse, the surfaces disagreed: commander rejected unknown `--flags` on the CLI, but Zod STRIPS unknown keys, so the MCP gateway's `run-command` params and direct library `commands[x].execute(...)` calls silently swallowed them and returned data that looked like it had obeyed. The 2026-07-24 delta audit found that on 5 of 7 delta commands (all six OData flags on list-todo-tasks-delta, all but `top` on both calendar deltas, `skip` on both drive deltas). Enforcement is a single wrapper applied at REGISTRY ASSEMBLY (`index.ts` maps every module through `withUnknownParamRejection`), with the allowed set read from `Object.keys(schema.shape)` so it cannot drift from what the command actually reads; the rejection names the flag in CLI spelling and carries `code: 'unknown_parameter'`. The wrap must live at assembly, not in composition: a library consumer reaches `commands[x].execute` directly and never passes through the CLI or the MCP gateway, so assembly is the only choke point all three share. Rejected: per-schema `.strict()` (identical behavior, 184 touch points, worse message, and it was BLOCKED anyway while aliases existed because the normalizer left both the alias key and the canonical key in the params bag); keeping `commandAliases` while dropping flag aliases (two names for four commands, for no consistency gain); renaming canonicals to the short forms (`--id` is ambiguous on multi-id commands). Zero renames: every alias already pointed at the more specific canonical, so deleting them left a coherent vocabulary. The one true divergence, `search-onenote-pages` naming its search term `--title-substring` while the other 7 search commands use `--query`, was closed by renaming it to `--query` (the CHANGELOG shows `--query` had been bolted on there as an alias for exactly that reason). Consequence: agents that learned `{id: ...}` params or an old command name now hard-error, which is the point.
Rule for next time: a flag that is accepted but not declared is worse than a missing flag, because the response looks obedient. When adding a surface, check what an UNDECLARED param does there, not just a valid one; the schema layer strips by default and will lie for you.
