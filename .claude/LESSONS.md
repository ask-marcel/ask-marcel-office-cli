## [gotcha] 2026-10-01 | errexit is off inside `$(...)`, so a failing `git diff` in a grouped command substitution read as "nothing changed" and the mutation gate passed

`mutate-changed.sh` built its scope as `files=$( { diff1; diff2; diff3; untracked; } | filter )` under `set -euo pipefail`. Inside a command substitution bash turns errexit off and the group returns its last command's status, so a diff that failed (no merge base on a shallow checkout, a base from rewritten history) printed git's error, then "no files in mutation scope changed", and exited 0 having mutated nothing; the script had the flaw before the split work too. The sources are now chained with `&&`, and `mutation-scope-selftest.sh` runs the real caller against an unrelated base and expects a non-zero exit.
Rule for next time: inside `$(...)`, chain commands with `&&` or give each its own assignment, and test a gate script's failure path through its caller, not only through its helpers.

## [gotcha] 2026-10-01 | `git diff -I` hands its pattern to the platform regex, and macOS has no `\b`, so an import filter written with `\b` matches nothing there

The mutation scope drops files whose only change is import lines with `git diff -I<regex>`. The plan's first pattern used `\b`; on macOS (Apple git 2.39 and Homebrew git 2.55 alike) a pure path change still reported `1 1`, so the filter silently did nothing. The shipped pattern in `scripts/mutation-scope.sh` is plain POSIX ERE that anchors the whole statement and allows no quote before ` from `, checked on both macOS gits and against GNU ERE. `mutation-scope-selftest.sh` pins it both ways: an import-only move mutates nothing, and an exported string that reads like an import stays in scope.
Rule for next time: write patterns handed to git (`-I`, `-G`, `--grep`, `log -E`) in POSIX ERE without `\b`, `\d` or lookarounds, and prove them in a selftest that runs on macOS and Linux.

## [mistake] 2026-09-28 | a value from a live probe or a real dump in a test fixture put real directory ids in a public repo

On 2026-08-27 the identity test in `pptx-comments.test.ts` copied `S::<UPN>::<Entra object id>` triples from a diagnostic dump of a real deck with only the emails swapped for `contoso.com`, so two real Entra object ids (`5c1a3800-...`, `b83acc04-...`) shipped in `e61f1e0`, and on 2026-09-19 the chat commits took the object id of the signed-in user from a live substrate probe as the `OID` fixture of three chat tests, public for nine days. Every gate passed both times, because gitleaks does not flag a bare GUID and no test asserts on one, and they were found only by a later visit to the fixture and by a reviewer who saw a GUID unlike the patterned placeholders (confirmed against `get-current-user` in the shell with neither id printed). Recovery without `rebase -i`: `git stash`, synthesize the ids, `git reset --soft HEAD~1`, `git commit --amend`, `git push --force-with-lease` (2026-08-27), and a targeted history rewrite of every commit since, force-pushed (2026-09-28), while old commits stay fetchable by SHA on the host until its GC, and npm never had them (tests are outside the `files` of the package). A replacement of only the recognisable half of a composite identifier reads as sanitised on review while the other half travels untouched.
Rule for next time: never derive test data from a live response or a dump of real content, whatever its shape: learn the format, write it down, and build the fixture from the placeholder vocabulary (`aaaaaaaa-1111-2222-3333-444444444444`, Contoso, Robin Chen) before the first commit, with each segment of a composite identifier (`S::a::b`, connection strings, URLs with ids) treated as real until replaced. Before you commit, grep the staged diff for literals from a live probe, and compare any random-looking GUID with the ids of the user (QA playbook, ground rule 9).
Merges: 2026-08-27 (mistake), 2026-09-28 (mistake).

## [gotcha] 2026-09-27 | Chat files, reactions and pasted images: the substrate's own shapes, and the one token the media service takes

Probed on 25 live chats. `properties.files` is a JSON STRING (`"[]"` on most messages) of `{ fileName, fileType, itemid, fileInfo: { fileUrl, shareUrl, siteUrl, serverRelativeUrl, shareID } }`; `itemid` is a SharePoint GUID, not a Graph driveItem id, so the links are what resolves. `properties.emotions` is an already-parsed ARRAY of `{ key, users: [{ mri: '8:orgid:<id>', time: <epoch ms>, value }] }`. A pasted image is an `<img itemtype="http://schema.skype.com/AMSImage" src="https://<x>.asm.skype.com|asyncgw.teams.microsoft.com/v1/objects/<id>/views/imgo">`; the media service answers the IC3 bearer (200) and 401s the chatsvcagg, basic and skype_token forms. IC3 also serves one message at `/v1/users/ME/conversations/{chat}/messages/{id}`.
Rule for next time: a URL read out of message content is untrusted: send a bearer only to an allowlisted host over https, and refuse before the request.

## [gotcha] 2026-09-26 | `/me/mailFolders` answers ten folders a page, so an eleventh top-level folder sits unseen on page two

Graph's default page for the mail-folder listings is ten, and a mailbox with eleven top-level folders showed ten and a cursor nobody followed; `/me/mailFolders/delta` walks the whole tree, nested folders included. `list-mail-folders` and `list-mail-child-folders` now ask for 100 a page unless `--top` says otherwise.
Rule for next time: a listing an agent reads once must ask for a page it can use; never trust a Graph default page size to cover a real mailbox.

## [gotcha] 2026-09-26 | Graph leaves the item out of a plain itemAttachment read, and an embedded mail's files live only in $value

`GET /me/messages/{id}/attachments/{id}` on an itemAttachment answers the attachment's metadata with no `item` property; the item comes only with `?$expand=microsoft.graph.itemattachment/item`, and even then an embedded MAIL arrives without its own attachments. `.../attachments/{id}/$value` answers the embedded mail's full MIME source (20.7 MB for a 15.5 MB item, attachments included), which the `.eml` reader renders. Every embedded item had failed live as "itemAttachment missing inner item" since the renderers shipped, while the tests passed: their fakes put `item` in the plain response.
Rule for next time: a fake Graph response is a hypothesis about Graph; before trusting a renderer that only a fake has fed, read the real endpoint once, and write the fake from what came back.

## [decision] 2026-09-26 | Diffs are two commands split by token tier, on jsdiff, capped at 1,000 edits

`diff-drive-items` (two files, basic token) and `diff-drive-item-versions` (a version against the live file, elevated token) share one render-and-diff core, but not one command: `needsElevatedToken` is per command, so a single command with optional `--other-*` flags would have demanded the elevated token to compare two current files. The line diff is jsdiff (`diff`, BSD-3-Clause, no dependencies of its own) rather than a hand-rolled Myers: its `maxEditLength` stops a diff of two unrelated documents early. The cap is 1,000 edits, not 5,000: jsdiff took about six seconds to give up on two unrelated 3,000-line renders at 5,000, and a document that changed in more than 1,000 lines is better read whole. Rejected alongside: immutable Outlook ids (`Prefer: IdType="ImmutableId"`) for the message that vanished between listing and read; they would change every mail command's ids for one sighting, so the not-found hint names the thread route instead.
Rule for next time: when a feature needs a secondary token on one path only, split the command along that line; and bound any quadratic library call by time on a pathological input before choosing its limit.

## [gotcha] 2026-09-26 | Graph never converts a historical version: `?format=html` answers the current page, and `?format=pdf` answers the version's raw bytes

Slice D probed `/drives/{d}/items/{i}/versions/{id}/content?format=html` on two Loop pages (5 and 8 versions): each call answered 200 `text/html` with the same SHA-256 as the current page, although the raw Fluid bytes of the versions differed (47,500 B against 63,000 B). The basic token got the same answer, although Graph refuses it the raw bytes of a version, which shows that Graph never read the version segment. `?format=pdf` on a historical version of a docx and of a Loop page answered `application/octet-stream`, the raw bytes with no conversion. Thus `download-drive-item-version --format markdown` returned the current Loop page as the old one. It now refuses with `unsupported_version_render`, and the summary says that pdf conversion of a version is a passthrough.
Rule for next time: prove that a Graph conversion (`?format=`) on a path that selects a version or a snapshot reads that version, by a comparison of its output with the output for the current item. A 200 proves nothing.

## [decision] 2026-09-26 | Meeting transcripts stay on the file route: `media/transcripts` is an unsupported segment on v1.0 and beta, with either token

A Teams meeting recording (`.mp4` in the organiser's OneDrive) carries `media`, `video` and `source` facets; its `media` holds the recording times and viewer settings, no transcript link. `GET /drives/{d}/items/{i}/media/transcripts` answered 400 `invalidRequest: Unsupported segment type` on v1.0 and on beta, signed with the Teams web token and with the elevated M365ChatClient token alike. With `OnlineMeetingTranscript.Read.All` absent from the fixed scopes, the Graph routes to a transcript are closed; no `download-recording-transcript` command. A transcript downloaded as a `.docx` or `.vtt` reads like any file.

Rule for next time: do not re-probe the Graph transcript routes without a scope change; the untested remainder is SharePoint's own `_api/v2.1/.../media/transcripts`, which needs a SharePoint-audience token the CLI does not hold.

## [decision] 2026-09-04 | Equivalent mutants are answered by refactoring the production code, and the worked example is naming a renamed attachment by its extension alone

`read-mail-attachment.ts` rebuilt the filename of a mislabelled attachment with its original stem across four branches (no dot, empty name, an already-correct extension, the normal case), but the result reached only `extensionOf` in the dispatch, so `report.csv` and `attachment.csv` routed to the same converter and 14 survivors stayed whatever tests were added. The fix was a refactor, never a skip list: the helper now returns `attachment.${ext}` (`extensionOf` lowercases, so an uppercase extension still works), which moved the file from 75.93 to 88.06, and tests of the six untested map entries reached 93.28. When the gate cannot tell two outputs apart, the code computes something that no caller consumes, and the deletion of that part is both the simplification and the fix. A negative assertion passes on a rejected input (`expect(text).not.toContain('## DOCX metadata')` stayed green when an enum mutant made `--include-metadata false` invalid), so the false case must first assert that the call succeeded. A flag that goes into a shared pipeline needs its own test, because `--include-metadata` had no test on this command or on the group-post converter.
Rule for next time: read a stubborn survivor as a question about the production code, not about the test. If a mutation of a value cannot change an output that a caller can see, do not add tests: delete the value.

## [decision] 2026-09-03 | group posts: read the author from `sender`, and list attachments when `hasAttachments` is true or the body has a `cid:` image

On 17 posts across the 3 readable groups, `from` equalled the group mail on 14 and `sender` differed from `from` on 10 (they matched only when the group posted as itself, 4, or the writer was an outside address, 3), and Outlook renders "sender on behalf of from", which `convert-group-post-to-markdown` prints. Graph reports `hasAttachments: false` for a message or post whose only attachments are inline (a post listed 7 inline images at `/posts/{id}/attachments?$select=...`, and `?$expand=attachments` inlined all 7 with `contentBytes`), so `renderMessageAsMarkdown`, which gated its metadata call on that flag, rendered placeholders named after the cid prefix and embedded nothing under `--inline-images true`. Fixed in `da81f7b`: the pipeline lists attachments when the flag or a `cid:` reference says so (`referencesCidImage`, a deliberate second copy of the regex of `get-mail-signature`, which had checked `src="cid:` since 2026-07-19), so `convert-mail-to-markdown` and `convert-group-post-to-markdown` name the placeholders, list inline images with their ids and embed them on request, and a body with no cid reference makes no extra call. Rejected: an unconditional attachment list (one call on every message for the few that need it) and a gate on `--inline-images true` alone (the default text mode also needs the names). The regression tests landed red first in the test files of both converters, and CI mutation gave 92.11 on the mail file, the two new survivors being equivalent regex variants.
Rule for next time: for any mail-shaped resource, read the author from `sender` when it differs from `from`. A summary flag is not the collection: when a body can reference an item that the flag does not count, gate on the reference too, and copy the exact predicate of a sibling command that has the right guard.
Merges: 2026-09-03 (gotcha), 2026-09-03 (decision).

## [gotcha] 2026-09-03 | `/groups/{id}/threads/{id}/posts` honors `$select` and `$expand` only: `$top`, `$skip`, `$orderby` and `$count` are silently ignored, `$filter` is rejected, and there is never a nextLink

A live probe on a two-post thread through `next-page` as a generic GET: `?$top=1` and `?$skip=1` returned both posts, `$orderby=receivedDateTime desc` and `asc` gave the same order, `$count=true` gave no `@odata.count`, and `$filter=receivedDateTime ge ...` answered `FilteringOnConversations: $filter is not supported on this collection.` The Learn page for conversationthread-list-posts agrees (select and expand, one relationship per request), while the threads collection accepts `$filter` on `IsLocked` only and conversations accept it on `lastDeliveredDateTime`. Thus `list-group-thread-posts` has `--select` and `--expand` only and no `pagination` flag, a caller sorts on `receivedDateTime` itself, and an incremental sync watermarks on `/conversations` (see the 2026-08-30 entry on group mailboxes).
Rule for next time: before you put a paging flag on a child collection, probe it on a thread with at least two items, because a one-item collection gives the same answer to each paging question. A silently ignored `$top` is worse than a missing one: the caller thinks that the slice happened.

## [decision] 2026-09-03 | Group posts ride the mail markdown pipeline through `renderMessageAsMarkdown(graph, resourcePath, options)`; post attachment commands are deferred

`convert-mail-to-markdown.ts` had `/me/messages/{id}` hardwired in three places, so instead of a second copy for posts the pipeline now takes the resource path (attachments always live at `${resourcePath}/attachments`), a header renderer and the attachment fetch hint, and the mail output stayed byte-identical (suite and mutation gate green, 92.56 on that file with only old survivors). `fetchInlineImageBytes` takes the resource path too, which cost `get-mail-signature` one line. Rejected: a `**Sender:**` line in the shared header renderer (it changes mail output for on-behalf-of messages), a thread fetch for the topic as a subject (one more call per post for a value the caller has), and `list-group-post-attachments` / `get-group-post-attachment` (not asked for, and `get-group-post --expand attachments` returns every attachment with its bytes, as the markdown footer says). The new commands have their own test files, not rows in the `commands.test.ts` tables, so an unattended run never edits an existing test file.
Rule for next time: when a second resource shape needs an existing multi-call pipeline, parameterize the resource path and the one rendering hook that differs, keep the output of the first caller byte-identical, and let the tests of the second caller kill the shared mutants of the pipeline.

## [gotcha] 2026-08-31 | elevated re-capture was slower than its 20s cap, and the fallback wipe made each prompt cause the next (corrects 2026-07-19 and 2026-08-15)

Reported as "nothing looks expired and I still get the login page": `acquireElevatedToken` polled for `elevatedRecaptureTimeoutMs` (20s), but a capture that SUCCEEDS took 41s through the bundled binary and 104s from source, so it always timed out, `login.ts` fell back to `getAccessToken({ force: true })`, and the `clearCookies()` of that dance deleted ESTSAUTHPERSISTENT, so the next run served a real sign-in page. Since `71c8e6d` the CALLER chooses the deadline (`awaitSignIn`, only `login`, gets `pollDeadlineMs`, and the rest keep the fail-fast cap that stops `list-chats` from a hang), the capture settles in ~10s and the cookie survives. This corrects two older entries: the 2026-07-19 spike (`scripts/spike-headless-elevated.ts`, on `m365.cloud.microsoft/search` and `teams.microsoft.com/v2/`, headless AND headed) and the 2026-08-15 re-probe concluded that conditional access on this tenant ignores a valid persistent SSO cookie, but the profile looked cookie-less (16 cookies, zero `ESTSAUTH*`) only because our own forced logins kept wiping it, and once a sign-in completed, ESTSAUTHPERSISTENT appeared with a 90-day expiry (claims `signin_state: ["kmsi"]`) and SURVIVED every later plain `login`. One finding of 2026-08-15 stays true: a cross-client redemption of the cached family refresh_token for the two elevated appids (c0ab8ce9 M365ChatClient, 4765445b OfficeHome), with and without `Origin: https://teams.microsoft.com`, returns AADSTS70000 invalid_grant on all four combinations, so elevated cannot be minted from the shared RT. A warm token cache still does not prove a warm browser profile: `scopes-check` with elevated available proves the CACHE only.
Rule for next time: before you conclude that a tenant or a service refuses something, check whether OUR OWN code destroyed it. When a timeout guards a path, measure the path SUCCEEDING at least once, because a cap shorter than the happy case looks like a broken feature, and its fallback is where the damage happens.
Merges: 2026-07-19 (gotcha), 2026-08-15 (gotcha), 2026-08-31 (gotcha).

## [decision] 2026-08-31 | The elevated deadline is chosen by the caller, never by inspecting the page: a silent SSO redirects THROUGH the AAD sign-in hosts

Between the two commits of the 2026-08-31 capture fix, a regression shipped and was removed: to fix "the window closes while I type my password", the code extended the deadline when the page URL was on `login.microsoftonline.com` and failed fast otherwise. A silent SSO passes through those same hosts on its way to the token (a capture completed with nobody at the keyboard after a visit to one), so the command path closed windows that were about to succeed. The signal is now the intent of the caller: `login` says that a person waits and gets the interactive budget, and a background command keeps the short cap, with no page inspection and no heuristic to tune. The progress line moved to the point where the short cap lapses, and it says only that the capture is slow and to complete a screen if one shows.
Rule for next time: an auth URL is a bad proxy for "a person is necessary" when the silent and the interactive flows share hosts. Prefer a signal that the caller knows for certain, and distrust a fix whose fast path is "close the browser sooner".

## [gotcha] 2026-08-31 | A substrate token can be REVOKED while still unexpired, and nothing in the CLI could recover it

The freshness of `chatsvcagg` / `ic3` came only from `*_expires_on`, but a second sign-in invalidates the substrate tokens of the previous session on the server: a token minted at 07:18 got a bare 401 at 13:47 with hours of stated life left, on both `teams.microsoft.com` and `teams.cloud.microsoft`, while one redeemed seconds later worked. Nothing could fix it: `scopes-check` reported the tier available, every Teams chat command got 401, and the hint said to run `login`, which cannot help because `warmSubstrateTokens` redeems only MISSING tiers. Only `login --force` (which costs the 90-day sign-in session) or a 24-hour wait recovered it. Since `6c5b166` a substrate 401 drops the token, redeems a new one from the shared refresh token over HTTP and replays the request ONCE, and the two substrate request paths are one `substrateGet`, so the recovery cannot reach one path and miss the other.
Rule for next time: an expiry claim tells when a token STOPS being valid, never that it still IS. For a token that a re-authentication elsewhere can invalidate, treat the first 401 as proof of death and get a new token, and make sure that the command a remedy hint names can reach that state.

## [gotcha] 2026-08-31 | Teams moved to `teams.cloud.microsoft`, and the region parser was anchored to the old host

`teams.microsoft.com` now 302s to `teams.cloud.microsoft`, and after the redirect every substrate call goes to the new host, but `parseChatsvcaggRegion` matched only the old host and returned null. The capture loop waits for a token AND a region, so a null region burned the full 20-second recapture deadline and then shipped the `emea` fallback, and on an APAC or AMER tenant every Teams chat command queried the wrong region with a success envelope. It worked on the day only because one early `/api/csa/` call landed on the old host before the redirect settled. Since `cc32dc3` the regex accepts either host as an explicit two-host alternation, never a wildcard, because the parsed region steers real request URLs and a lookalike host must not set it. Token capture did not change (same appid, same audiences), and both hosts serve the substrate API the same way, so the call hosts of `graph-client` stay as they were.
Rule for next time: when a vendor consolidates domains, grep for the OLD host in matchers, not only in navigation targets. A redirect keeps navigation working and silently breaks each regex anchored to the old landing host, and the failure shows as wrong data, not as an error.

## [gotcha] 2026-08-31 | The mutation gate reported scores it had not measured, in three separate ways

The gate let pushes through and reported scores it had not measured, in three ways. (1) On a main push CI ran `BASE=HEAD~1`, so a push of three commits mutated only the files of the tip, and CI now bases on `github.event.before`. (2) `mutate-changed.sh` filters `*.test.ts`, so a tests-only commit gave ZERO files, and the gate printed "no files in mutation scope changed" and passed, which hides a test WEAKENED against untouched source, and a changed `X.test.ts` now pulls in `X.ts`. (3) `--force` re-tests every mutant but still READS the incremental file and scores the whole report, so one tree scored 95.77 locally and 89.14 in CI, and `--incremental false` does not exist (Stryker declares `--incremental` as a valueless flag, so a value is read as a config path and the run stops on `Invalid config file "false"`), so both scripts point `--incrementalFile` at a throwaway under `mktemp`. The inflated number was reported as fact before CI contradicted it.
Rule for next time: a gate that can silently measure NOTHING is worse than no gate, because it reports success either way. When one run disagrees with another on the same tree, find the mechanism before you believe either number, and check what the gate does with an empty input set.

## [gotcha] 2026-08-30 | `mail-editor-reference-message-container` wraps AUTHORED text on Outlook mobile, so the id alone cut a structured message down to its greeting

The id looks like a quote wrapper and sat in `QUOTE_BOUNDARIES` beside `divRplyFwdMsg` and `appendonsend`, but on a message written in Outlook mobile the container held the ENTIRE body and the signature, with no `From:` / `Sent:` / `To:` / `Subject:` label, no `<hr>` and no separator div. `convert-mail-to-markdown` returned 9 of 5,367 visible characters, reported `ok` and said only "quoted reply chain stripped", and the loss hits the most valuable mail, because a long structured message is what the heuristic misreads. A probe of the WHOLE thread settled it: 2 of its 16 messages were cut on the container and on nothing else, so a deletion of the rule would have kept two reply chains, and every container around a real quote opened a From/Sent header within 229 characters (+177 and +229 in two Outlook renderings), while the false positive had none. Since `1b854a0` the container is a confirmed marker with a 600-character window, scanned for every container in the body, so a long text inside one still gets the cut at the quote below it. All 16 boundaries were measured again: 15 byte-identical, the false positive gone.
Rule for next time: a vendor id that NAMES a quote region is evidence about the DOM of the editor, not about a quote, so confirm it against content before you cut on it. When a detection rule misfires, probe the whole conversation before you change it: one message shows that the rule is wrong, only the corpus shows what depends on it.

## [decision] 2026-08-30 | The quote stripper stays rule-identity based; no proportion guard, and the note reports the removed share instead

The suggested fix "never strip when the result removes most of the body" fails on the real thread: the destroyed message kept 0.2% of its readable text, and real short replies above long chains kept 1.7%, 2.5%, 2.9%, 3.0%, 4.3%, 5.6% and 9.1%, so no threshold separates a swallowed body from "Thanks" above a 20 KB chain. The rule that fired separates them: `divRplyFwdMsg`, `appendonsend` and `gmail_quote` are unambiguous vendor markers, while the mobile container and the bold From-label are inferences to confirm against nearby content. Also rejected: deletion of the container rule (two messages of the corpus depend on it), and a note only when the strip looks suspicious (the caller owns that judgement). Since `82ff19f` the note gives the share of READABLE text removed, as in `quoted reply chain stripped (removed 90% of the body text)`, because by HTML length a reply that kept 9% of its visible text measures 43% intact. The share is measured from the boundary, never from the stripped output (its marker adds 66 characters), and a body that is only a marker reports 100.
Rule for next time: before you add a size or ratio guard to a heuristic, measure that ratio on the real positives AND on the real false positive. If the two ranges overlap, the guard is a coin flip, and the honest fix is to REPORT the number, not to act on it.

## [gotcha] 2026-08-30 | quote-stripper spellings: a tag-name regex needs a lookahead, and the Outlook reply divider comes in two hues and in a CSS longhand

`<(?:b|strong)[^>]*>` matches `<br>`, `<br/>`, `<body>`, `<bdi>`, `<big>` and `<blockquote>`, because `[^>]*` eats the rest of the tag NAME, so the "must be bold" half of the From-label guard never checked bold (`Dear all,<br>De: ops` with a Date label in the next 400 characters was a full header match), and a tag-name match needs a lookahead, `<(?:b|strong)(?=[\s>])[^>]*>`. The Outlook reply divider is `border-top: solid #E1E1E1` (desktop Word renderer) or `#B5C4DF` (Mac / mobile), so `QUOTE_BOUNDARIES` holds `/<div[^>]*border-top:\s*solid #(?:E1E1E1|B5C4DF)/i` (2026-07-19), and new Outlook writes the same rule in longhand (`border-width:1pt medium medium; border-style:solid none none; border-color:rgb(181,196,223) currentcolor currentcolor`), with no hex and the side chosen by `border-style`, so no wider hex pattern can match it. Both fixes landed in `6b6c045`, and every boundary in the 16-message corpus stayed byte-identical. The generic Word `windowtext` top border, in four of those bodies, was deliberately NOT added, because it draws ordinary bordered paragraphs and tables. A bare `\s*`→`\S*` regex-flag mutant on the divider line is an accepted equivalent, since real Outlook writes `border-top:solid` with no space.
Rule for next time: an HTML tag regex must anchor the end of the tag NAME. A CSS-value regex sees one spelling of several (hex or `rgb()`, shorthand or longhand, the side in the property or in a sibling declaration): probe real bodies of the clients in play, cover each new hue with an it.each divider test, and when in doubt prefer the spelling that cuts LESS.
Merges: 2026-07-19 (gotcha, two hues), 2026-08-30 (gotcha).

## [decision] 2026-08-30 | `login --force` keeps `clearCookies()` although it deletes the 90-day KMSI session, and the localStorage-only wipe is not taken

The wipe in the "already signed in" branch of `acquireBothTokens` exists because the BASIC token is read off the OAuth GRANT RESPONSE, so the grant must fire again with the listener attached, but it also deletes `ESTSAUTHPERSISTENT`, the ~90-day cookie that AAD writes on "Stay signed in?", and leaves only session-scoped `AADSSO` / `esctx` plus telemetry (`buid`, `fpc`, `brcap`, `OH.FLID`), so the next capture shows a bare sign-in form. The diagnosis came from a dump of `Default/Cookies` with sqlite3, with `is_persistent` and `expires_utc` per cookie name, because the host list alone looks healthy (the telemetry cookies live long). Since `a585857` plain `login` no longer sends ordinary elevated expiry through the dance, so the wipe runs only on an explicit `--force` or when silent SSO fails, and a prompt on the button that means "re-capture everything" is defensible (the 2026-08-31 capture fix made the second case rare). ## [gotcha] 2026-06-13 | an additive error-envelope field must be threaded through ALL THREE layers (infra → composition → presenter) or CLI consumers never see it

## [gotcha] 2026-07-15 | Guest / B2B UPNs carry `#EXT#`; a raw `#` in a `/users/{id}` path is silently dropped as the URL fragment — encodeURIComponent the userId

This is invisible to unit tests that only use `@`-style UPNs and to `new URL()` normalization (which percent-encodes query spaces/quotes but CANNOT encode a path `#` — structurally it is already the fragment start). Microsoft's docs are explicit: for B2B UPNs "you must encode the reserved character '#' as '%23' in the request URL". Fixed by wrapping the id segment in `encodeURIComponent` across `get-user` (new) + 7 shipped siblings (`get-user-manager`, `get-shared-mailbox-message`, `list-shared-mailbox-messages`, `list-shared-mailbox-folder-messages`, `list-shared-calendar-events`, `list-user-direct-reports`, `list-shared-calendar-view`). Verified live: `list-user-direct-reports` / `get-user-manager` with a `%40`-encoded real UPN resolved the user and returned data — so `@`→`%40` is accepted by Graph on the wire (the official SDKs encode path params the same way). The name path in `get-user` does NOT need this: its value sits in a `$search="..."` QUERY literal, where `new URL()`/`fetch` percent-encodes spaces and the `"`-strip handles injection; only PATH segments have the `#`-fragment hazard.
Rule for next time: any Graph path segment that can hold a caller-supplied UPN MUST be `encodeURIComponent`'d — a GUID passes through unchanged, `@`→`%40` and `#`→`%23` are both accepted. Guard it with a fixture that feeds `alice_contoso.com#EXT#@fabrikam.onmicrosoft.com` and asserts the path contains `%23EXT%23` and NOT `#EXT#` (doubles as the mutation guard on the `encodeURIComponent` call). `capturedUrl` in commands.test.ts returns the raw pre-fetch string, so the assertion sees the encoding directly. Note the `$`-prefixed-UPN OData caveat (`/users('$foo')`) is a separate, rarer case encodeURIComponent does not solve, but `$` is not a legal UPN character so it does not arise here.
